# 設計判断の記録（my-harness）

このリポジトリでの判断と、その理由・不採用案を残す。古い判断は消さず「廃止」にする。
全部を読まず、見出しから関係するものを選んで読む。見出しは、それだけで何を決めたかが分かる一文にする。

## D-001 エージェントへの指示は AGENTS.md を正にし、CLAUDE.md は `@AGENTS.md` で読み込む

- **日付**: 2026-11-07
- **状態**: 採用

- **見直す条件**: Claude Code が `AGENTS.md` を直接読むようになったとき

## D-003 開発ガイドラインはテーマ別に分け、プロジェクトに必要なものだけをコピーする

- **日付**: 2026-11-07
- **状態**: 採用
- **決定**: オーナーの開発ガイドラインを `assets/templates/guidelines/` に4つ（documentation / design / ui / coding）に分けて置く。「AI エージェントとの作業」の章は `assets/templates/AGENTS.md` の作業ルールに統合する。生成時は、プロジェクトに当てはまるものだけを `docs/guidelines/` にコピーする
- **理由**:
  - UI のないプロジェクトに UI と配色の原則を入れても読まれるだけで役に立たず、コンテキストを圧迫するため
  - エージェントへの指示は AGENTS.md に集める方が、毎回確実に読まれるため（ガイドラインと AGENTS.md の両方に書くと重複する）
  - コピーしておけば、プロジェクトのリポジトリだけで完結し、どのエージェントでも読めるため
- **不採用案**:
  - 1ファイルのままコピーする: 不要な章まで入るため
  - プロジェクトにコピーせず、共通の場所（`~/.claude/` など）を参照させる: そのマシンの Claude Code でしか読めず、リポジトリを見ただけでは原則が分からないため
- **見直す条件**: ガイドラインを複数プロジェクトで頻繁に更新するようになり、コピーの食い違いが問題になったとき

## D-005 progress.md は「今の状態」だけにし、作業履歴は持たない

- **日付**: 2026-11-07
- **状態**: 採用（追記型の進捗ログは廃止）
- **決定**: `progress.md` には、進行中・次にやること・注意だけを書き、毎回書き換える。エージェントの失敗だけは `failures.md` に分けて残す
- **理由**:
  - 時系列の履歴に書いていた内容（何を変えたか・なぜ・次に何をするか）は、git の履歴・`decisions.md`・今の状態と重なっていた
  - 追記型だと古い「次にやること」が残り、どれが有効か分からなくなる（このリポジトリの進捗ログで実際に起きた）
  - 長くならないので、圧縮や移動の仕組みがいらない
  - 失敗は時間がたっても参照する（同じ失敗が2回起きたかの判断に使う）ため、書き換える progress.md とは分ける
- **不採用案**:
  - 1ファイルの中を「今の状態」と「履歴」に分ける: 履歴の大部分が git と重なり、長くなったときの対処も必要になるため
  - 履歴が長くなったら hook で検出し、移動や圧縮をユーザーに確認する: 履歴そのものを持たなければ不要なため
  - セッションごとに1ファイル: 最新の状態を知るのに複数のファイルを読む必要があるため
  - 失敗を progress.md の中の節に書く: 書き換えるファイルに混ぜると、消えてしまうため
- **見直す条件**: git にコミットしない期間が長いプロジェクトで、経緯が分からなくなる問題が起きたとき

## D-006 hook の処理は共有スクリプトに1つだけ書き、ツールごとの設定は呼ぶだけにする

- **日付**: 2026-11-07
- **状態**: 採用
- **決定**: hook の処理は `scripts/hooks/*.sh` に書き、`.claude/settings.json` と `.codex/hooks.json` はそれを呼ぶだけにする。ファイル編集の hook は、両ツールの入力形式（Claude Code のパス、Codex のパッチ）を読み、エージェントが編集したファイルだけを対象にする。危険なコマンドの一覧は `block-dangerous.sh` だけに書き、Claude Code の `deny` には書かない。formatter や lint は、pre-commit と CI にも置くことを勧める
- **理由**:
  - Claude Code と Codex は設定ファイルの場所が違うが、hook の形はほぼ同じで、処理を共有できる
  - hook はそのエージェントでしか効かず、ツールを使わない書き換えもすり抜ける。pre-commit と CI ならどれにも効く
- **不採用案**:
  - ツールごとに hook の処理を書く: 同じ処理が2か所に分かれ、片方だけ直されるため
  - hook をやめて pre-commit と CI だけにする: 危険なコマンドを実行前に止めることや、編集直後にエージェントへ結果を返すことができないため
  - ファイル編集の hook で、入力を読まず `git diff` の変更ファイルを全部整形する（一度採用した）: ユーザーが作業中のファイルまで整形してしまうため
  - 危険なコマンドを `deny` と hook の両方に書く（一度採用した）: 一覧が2か所に分かれるうえ、Codex には `deny` がないため
- **見直す条件**: どちらかのツールの hook の形が大きく変わったとき

## D-007 モデルごとの指示ファイルは作らない

- **日付**: 2026-11-07
- **状態**: 採用
- **決定**: 指示はモデル名ではなく行動で書く。どのツール・モデルで起きた失敗かは `failures.md` に記録し、モデルを更新したときに見直す
- **理由**: モデルの更新は速く、モデル別のファイルはすぐ古くなる。古い指示は新しいモデルの邪魔になる。`failures.md` に残せば、モデルごとの癖を追いつつ、見直しの対象を1か所にまとめられる
- **不採用案**: `models/opus-5.5.md` のようなモデル別の指示ファイル: 見直しの対象が増え、どのモデルが読んでいるかも保証できないため
- **見直す条件**: モデルごとの違いが大きく、行動で書いた共通の指示では対応できない失敗が続いたとき

## D-008 テンプレートの行に、レベルと条件の目印をつける

## D-010 変更の範囲を「関係するまとまり」と定義し、継ぎ足さず全体として書き直す

- **日付**: 2026-11-07
- **状態**: 採用
- **決定**: 変更の範囲を「目的に関係するまとまり（関数・モジュール・ドキュメントの節）は、変更後の全体として書き直す。関係しないものには触らない」と定義する。完了前には、変更したまとまりを差分ではなく頭から読み直し、前の版を知らない人が読んでも最初からこう書かれていたように見えるかを確かめる。ハーネスの原則（原則10）、テンプレートの AGENTS.md、ガイドラインの3か所に入れる
- **理由**:
  - 修正を重ねると、コード・コメント・ドキュメントに継ぎ足しの跡が積もる（このリポジトリでも起きた）
  - 以前の「必要な範囲だけ変更する」は、無関係な変更を防ぐためのルールだったが、関係するまとまりの書き直しまで避ける方向に働いていた
  - 確認が差分だけだと、変更した部分が正しければ通ってしまい、全体のまとまりを誰も見ない
- **不採用案**:
  - 「変更を最小にする」ルールのまま、注意書きを足す: ルール同士がぶつかり、最小にする方が優先されやすいため
  - 経緯の言葉（「変更」「以前は」「v2」など）をコメントから検出する検査を今すぐ入れる: 見つけられるのは一部だけで、まずは手順と評価で足りるか確かめるため（原則7）
- **見直す条件**: 手順と評価だけでは継ぎ足しが続くとき

## D-011 ガイドラインには、その種類のどのプロジェクトにも当てはまる原則だけを書く

- **日付**: 2026-11-07
- **状態**: 採用
- **決定**: ガイドラインに入れるのは、そのガイドラインをコピーするどのプロジェクトにも当てはまる原則だけにする。一部の画面や機能にだけ当てはまるもの（キーボード操作、ダークモード、設定画面での反映のしかた、データの上に重ねる表示、前回の選択を初期値にすることなど）は入れず、必要なプロジェクトが `docs/decisions.md` に書く
- **理由**: 当てはまらない原則は読まれるだけでコンテキストを圧迫し、無理に当てはめようとする判断の誤りも生む。D-003 でガイドラインを分けた理由と同じ
- **不採用案**: 「〜の場合は」と条件を付けて残す: 条件付きの項目が増えると、どれが自分のプロジェクトに関係するかを毎回判断させることになるため
- **見直す条件**: 同じ局所的な決定を、多くのプロジェクトで毎回書くようになったとき

## D-012 増え続ける記録（decisions.md・failures.md）は、見出しから関係する項目だけを読ませる

- **日付**: 2026-11-08
- **状態**: 採用
- **決定**: decisions.md と failures.md の見出しは、それだけで中身が分かる一文にする。エージェントには全文ではなく、要件と、見出しから選んだ関係する項目だけを読ませる。テンプレートの AGENTS.md・decisions.md・failures.md、評価役の例、このリポジトリの AGENTS.md・decisions.md・failures.md に入れる
- **理由**: どちらも項目を消さずに残すため増え続け、「実装の前に decisions.md を読む」という指示のままでは、作業のたびに全文がコンテキストに入る。AGENTS.md は約100行の上限、progress.md は書き換えで大きくならないが、この2つには歯止めがなかった
- **不採用案**:
  - 大きくなったら「廃止」や「対策済み」の項目を別ファイルに移す: まだ大きくなっておらず、今入れても防ぐ失敗がないため（原則7）。見直す条件に回す
  - 判断を1件1ファイルに分ける: 見出しの一覧を見るのにファイルを開く手間が増え、まとまりも見えにくくなるため
- **見直す条件**: どちらかのファイルが約300行を超えたとき、または見出しだけでは関係する項目を選べない失敗が起きたとき

## D-013 SKILL.md は 8,000 バイト以内にし、流れと参照ファイルを読むタイミングだけを書く

- **日付**: 2026-11-08
- **状態**: 採用
- **決定**: `SKILL.md` は 8,000 バイト以内にする。設計の見せ方・テンプレートの一覧・目印・埋め方は `references/generation.md` に移す。生成先で skill を作るときの上限と、Codex の `AGENTS.md` の上限（32KiB）は `references/agent-tools.md` に書く。あわせて、検証に「その行がなければエージェントが間違えるか」で AGENTS.md の一般論を消す確認を入れる
- **理由**:
  - Codex は skill の本文を 8,000 バイト（`MAX_SKILL_PROMPT_BYTES`）で切り、警告が出てもモデルが残りを読まずに進むことがある（openai/codex#37463、everyinc/compound-engineering-plugin#1412）。以前の SKILL.md は約 11,900 バイトで、検証と育成の手順が届かなかった
  - 自動生成した AGENTS.md は冗長で一般的になり、役に立たないという指摘がある。行数の上限だけでは中身の必要性を確かめられない
- **不採用案**:
  - 500行以内の目安のままにする: 日本語は1文字が約3バイトで、行数では上限を守れないため
  - 大きさを検査するスクリプトを入れる: 今は `wc -c` で確かめれば足り、守られない失敗もまだ起きていないため（原則7）
- **見直す条件**: Codex の上限が変わったとき、または SKILL.md が上限を超える変更が繰り返されたとき

## D-014 複数の意味に取れる依頼は、解釈を挙げて確認させる。AGENTS.md にはコードを読んでも分からないことだけを書く

- **日付**: 2026-11-08
- **状態**: 採用（確認の場面と形は D-024 で変えた）
- **決定**: テンプレートの AGENTS.md の「着手前」に、依頼が複数の意味に取れるときは解釈を挙げて確認する手順を入れる。小さく取り消しやすい作業は、前提を伝えて進めてよい。「作業中」に、依頼にない機能・設定・抽象化を足さないことを入れる。生成時は、コードを読んでも分からないこと（正確なコマンド、真似してはいけない書き方、リポジトリにない決定）だけを書き、規約はコード片で示す。守られない指示は強調で直さず、より確実な仕組みに移す
- **理由**: オーナーの要望に加え、次の資料で同じ指摘があった。Claude Code のベストプラクティス（CLAUDE.md に書くもの・書かないもの、強調では直らない）、andrej-karpathy-skills の CLAUDE.md（解釈が複数あれば黙って選ばない、頼まれていない機能を足さない）、GitHub の 2,500 件の agents.md の分析（コマンドを早く・オプションまで、説明よりコード例、技術はバージョンまで具体的に）
- **不採用案**:
  - どんなときも確認させる: 小さな作業まで止まり、確認が多いと読まずに答えるようになるため
  - GitHub の分析にあるエージェントの人格（ペルソナ）の設定: 作業ルールと失敗の記録で足り、どの失敗を防ぐかを言えないため（原則7）
- **見直す条件**: 確認が多すぎて作業が進まない、または確認せずに進める失敗が続くとき

## D-015 試した結果は feedback/ に1回1ファイルで残し、同じ問題が2回出たら skill を直す

- **日付**: 2026-11-08
- **状態**: 採用
- **決定**: skill を実際のプロジェクトで試した結果を、このリポジトリの `feedback/` に1回1ファイルで残す。記録は git に入れず手元にだけ置き、skill を直した理由はこのファイルに書く。材料は、テンプレートと生成物の差分、生成したときの会話の記録、skill の最後の報告（合わなかった箇所・迷った点）、生成先の `docs/failures.md`。同じ問題が2回の試行で出たら直す。あわせて、生成時に作成時のツールとモデルを生成先の `docs/decisions.md` に残させる
- **理由**: 生成先の改善はそのプロジェクトの中で閉じていて、skill に戻る道がなかった。記録を git に入れないのは、試したプロジェクトの中身（何を作っているか、使っている技術）が入り、リポジトリを GitHub に置くと共有されるため。モデルの特徴に合わせて中身を変えるのではなく、作成時のモデルを記録するだけにするのは、D-007 と同じ理由（特徴の記述はすぐ古くなる）
- **不採用案**:
  - 振り返り用の skill を今作る: 手順がまだ決まっておらず、作り直しになるため。手での振り返りを2回やって固まったら作る（原則7）
  - 失敗ごとの再現プロンプトや `evals/` を今作る: 何を確かめるべきかは、試してみないと決められないため
  - ヒアリングでモデルを聞き、特徴に合わせて生成する: D-007 と同じ理由。モデルの癖は failures.md の記録から分かる
  - 試した結果を skill の中（`skills/harness-creator/`）に置く: 生成先の事情が skill に混ざるため
  - 記録を git に入れ、プロジェクトの説明だけ一般的な言い方にする: 書くたびに言い換えに気を配る必要があり、漏れたときに履歴に残るため
- **見直す条件**: 試行が増えて feedback/ を読み切れなくなったとき、または振り返りの手順が2回で固まったとき

## D-016 評価役のサブエージェントを L1 から標準で入れ、懐疑的に判定させる

- **日付**: 2026-11-08
- **状態**: 採用

## D-023 block-dangerous.sh は、コマンドの中の位置によらず止め、作業中の変更を捨てる git の操作も止める

- **日付**: 2026-11-10
- **状態**: 採用
- **決定**: テンプレートの `block-dangerous.sh` のパターンを、コマンド名の始まり・git のオプション・同じコマンドの中の引数・引数の終わりの部品で組み立てる。止めるものに、`git clean -f`、`git checkout .`・`git checkout -f`、`git restore .`、`find … -delete`、`git push origin +main` の形を足す。調べる前に、行の継続とタブを揃え、止めない形（`git rm`、`git clean -n`、`--worktree` のない `git restore --staged`）を当たらない名前に置き換える。jq がないときは JSON 全体を、改行とタブを戻してから調べる

  - 足した git の操作は、追跡していないファイルや作業中の変更を取り戻せない形で消す。テンプレートの AGENTS.md の「既存の作業中の変更も消さない」「取り消しの難しい git 操作」に当たる
- **不採用案**:
  - `git restore --staged .` と `git clean -n` も止める: ステージを外すだけ、消すものを表示するだけで、何も消えないため
  - コマンドを構文として解析する: 引用符や変数の展開まで追うことになり、hook のスクリプトとしては重い。文字列の中の `rm -rf`（コミットメッセージなど。jq がないときは JSON のほかの項目も）に当たることは残るが、止まってもユーザーに頼めば済むため
  - 入力と期待する終了コードを並べたテストを、このリポジトリに置く: 今回は手で確かめた。パターンをもう一度直すことになったら作る（原則7）

  - 計画の承認（Claude Code の plan mode）を使わせる: 確実に止まるが、計画を書く分が重く、短い確認でよいという要望に合わないため。Codex にも同じものがない
  - どんなときも返させる: D-014 と同じ理由（小さな作業まで止まり、読まずに答えるようになる）
- **見直す条件**: 確認が多すぎて作業が進まない、または返すべき場面で返さずに進めて外す失敗が2回起きたとき

## D-026 テスト・lint は失敗だけを出す形で書かせ、ガイドラインは見出しから選んだ節だけ読ませる

- **日付**: 2026-11-14
- **状態**: 採用
- **決定**:
  - 生成の手順（`references/generation.md`）とテンプレートの AGENTS.md の目印で、テスト・lint・型チェックのコマンドを、通った項目を並べず失敗だけを出す形で書かせる。失敗したときに場所と理由が出ることも確かめさせ、警告を隠すオプションは使わせない
  - テンプレートの AGENTS.md と evaluator で、ガイドラインはファイルごとではなく、`grep -n "^##" docs/decisions.md docs/guidelines/*.md` で decisions.md と一緒に見出しを一覧にし、関係する節だけを読ませる。ガイドラインを1つも入れないときは、生成の手順でコマンドから `docs/guidelines/*.md` を消させる（zsh では当たるファイルがないとコマンド全体が止まるため）
- **理由**:
  - オーナーが、生成したハーネスでのトークンの消費を抑えたいと言い、5つの案から、質を落とさずにすぐ入れられる2つを選んだ
  - D-021 で数えた記録では、Bash と Read の出力が3〜5割を占めた。テストと lint は作業のたびと評価役の確認のたびに実行されるが、出力を絞る書き方はテンプレートになかった
  - ガイドラインは4つで約15KB あり、本体と評価役がそれぞれファイルごと読んでいた。decisions.md ではすでに見出しから選ばせている（D-021）ので、同じ形にした
  - AGENTS.md は約100行の上限にあるため、行は足さず、既存の行と目印を書き換えた
- **不採用案**:
  - evaluator を安いモデル（`model: sonnet` など）で動かす: 指摘の質が落ちないかを試していないため（qa は D-027）
  - 評価役を呼ぶ場面を、ロジックの変更や複数のファイルにまたがる変更に絞る: 確かめる回数が減るため、試してから決める
  - AGENTS.md を短くする: 毎回読み込まれるがキャッシュが効き、減る量が小さいため。次に行を足すときに、詳しい内容を `docs/` に分けるかと一緒に考える
  - 出力を `| tail` で切る: 終了コードが隠れたり、失敗の詳細が切れたりするため
  - 警告を隠すオプション（ESLint の `--quiet` など）で減らす: 直すべき警告まで見えなくなるため
- **見直す条件**: 失敗だけを出す形で、失敗の原因が分からず全体を実行し直すことが続くとき。節だけ読んだことで、ガイドラインの別の節にある原則を見落とす失敗が起きたとき

## D-027 探す作業の Explore と qa は Haiku で動かす

- **日付**: 2026-11-14
- **状態**: 採用
- **決定**:
  - テンプレートの CLAUDE.md で、ファイルを探す作業を `Explore` に任せるときは、呼び出すときに `model: haiku` を指定させる。Web の調べものはモデルを指定しない
  - qa を作るときは、frontmatter に `model: haiku` を入れる（`references/generation.md`）。evaluator はモデルを指定しない
- **理由**:
  - オーナーの判断。生成したハーネスでのトークンの消費を抑えるため（D-026 の続き）
  - Claude Code の公式ドキュメント（https://code.claude.com/docs/en/sub-agents ）を調べたエージェントの要約によると、組み込みの Explore は呼び出した会話のモデルを引き継ぎ、モデルは呼び出すときの指定がいちばん優先される。指定しないと、探すだけの作業も本体と同じモデルで動く。原文はまだ確かめていない
  - qa は画面の snapshot などの出力でトークンを多く使う。どこを試すかを自分で判断する役でもあるので、Haiku で見落としが出ないかは試していない。オーナーの判断で、試す前に入れる
  - evaluator は懐疑的に確かめて指摘する役で、質が落ちないかを試していないため、指定しない（D-026 の不採用案）
- **不採用案**:
  - `.claude/agents/Explore.md` を置いて組み込みの Explore を上書きする: 公式ドキュメントでは同じ名前の定義で上書きできるが、Explore の指示を自分で書くことになり、Claude Code の更新に追いつけず古くなるため（原則8）
  - 環境変数 `CLAUDE_CODE_SUBAGENT_MODEL`（と `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`）で決める: すべてのサブエージェントに効き、evaluator まで Haiku になるため
- **見直す条件**: Haiku の Explore が結論を取り違えたり、探し漏らしたりして、本体が読み直すことが続くとき。Haiku の qa が操作の失敗を見落とすとき。Claude Code の Explore の既定のモデルが変わったとき
