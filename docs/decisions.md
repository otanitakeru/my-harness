# 設計判断の記録（my-harness）

このリポジトリでの判断と、その理由・主な不採用案を残す。古い判断は消さず「廃止」にする。
1項目は数行にする（D-031）。「状態」は、廃止や一部の変更があった項目にだけ書く。
全部を読まず、見出しから関係するものを選んで読む。見出しは、それだけで何を決めたかが分かる一文にする。

## D-001 エージェントへの指示は AGENTS.md を正にし、CLAUDE.md は `@AGENTS.md` で読み込む

- **決定**: 指示の本体は `AGENTS.md` に書く。`CLAUDE.md` は `@AGENTS.md` と Claude Code 専用の追記だけにする
- **理由**: Codex など他のエージェントでも同じ指示を使えるため
- **不採用**: シンボリックリンク（zip 化や Windows の git で壊れ、専用の追記もできない）
- **見直す条件**: Claude Code が `AGENTS.md` を直接読むようになったとき

## D-002 作るものは配布用テンプレートではなく、ハーネスを作る skill にする

- **決定**: `skills/harness-creator/` に skill を作る。構成は `skill-creator` に合わせ `SKILL.md` + `references/` + `assets/`。名前は kebab-case
- **理由**: 共通テンプレートのコピーではプロジェクトに合わない部分が出る。skill なら調べてヒアリングし、合う部分だけを作れる
- **不採用**: `harness/` フォルダを各プロジェクトにコピーする（調整を毎回手でやることになる）

## D-003 開発ガイドラインはテーマ別に分け、プロジェクトに必要なものだけをコピーする

- **決定**: オーナーのガイドラインを `assets/templates/guidelines/` に4つ（documentation / design / ui / coding）に分け、当てはまるものだけを生成先の `docs/guidelines/` にコピーする。「AI エージェントとの作業」の章はテンプレートの AGENTS.md に統合する
- **理由**: 当てはまらない原則はコンテキストを圧迫するだけ。コピーすればリポジトリだけで完結し、どのエージェントでも読める
- **不採用**: 1ファイルのままコピーする。共通の場所（`~/.claude/`）を参照させる（そのマシンでしか読めない）
- **見直す条件**: 複数プロジェクトでの更新が増え、コピーの食い違いが問題になったとき

## D-004 ハーネスの原則とコードの原則を分ける

- **決定**: ハーネスの原則は `references/principles.md`（skill が読む）、コードの原則は `assets/templates/guidelines/`（生成先にコピー）に置く
- **理由**: 読む人と使う場面が違うため

## D-005 progress.md は「今の状態」だけにし、作業履歴は持たない

- **状態**: このリポジトリでは採用。生成先では廃止（→ D-032）
- **決定**: progress.md には進行中・次にやること・注意だけを書き、毎回書き換える。失敗は `failures.md` に分けて残す
- **理由**: 履歴は git・decisions.md と重なり、追記型だと古い「次にやること」が残る（このリポジトリで起きた）。失敗は後で「2回目か」の判断に使うので消えない場所に置く
- **不採用**: 1ファイルの中を今と履歴に分ける。セッションごとに1ファイル
- **見直す条件**: コミットしない期間が長いプロジェクトで、経緯が分からなくなったとき

## D-006 hook の処理は共有スクリプトに1つだけ書き、ツールごとの設定は呼ぶだけにする

- **決定**: 処理は `scripts/hooks/*.sh` に書き、`.claude/settings.json` と `.codex/hooks.json` は呼ぶだけ。編集の hook は両ツールの入力を読み、エージェントが編集したファイルだけを対象にする。危険なコマンドの一覧は `block-dangerous.sh` だけに書く。formatter・lint は pre-commit と CI にも置くことを勧める
- **理由**: 処理を2か所に書くと片方だけ直される。hook はそのエージェントにしか効かない
- **不採用**: hook をやめて pre-commit と CI だけにする（危険なコマンドを実行前に止められず、編集直後にエージェントへ結果を返せない）。`git diff` の変更ファイルを全部整形する（一度採用した。ユーザーの作業中のファイルまで変わる）。危険なコマンドを `deny` にも書く（一度採用した。2か所に分かれ、Codex に `deny` がない）
- **見直す条件**: どちらかのツールの hook の形が大きく変わったとき

## D-007 モデルごとの指示ファイルは作らない

- **決定**: 指示はモデル名ではなく行動で書く。どのモデルで起きた失敗かは `failures.md` に記録する
- **理由**: モデルの更新は速く、モデル別のファイルはすぐ古くなる
- **見直す条件**: 共通の指示では対応できないモデルごとの失敗が続いたとき

## D-008 テンプレートの行に、レベルと条件の目印をつける

- **決定**: テンプレートの行・節に `<!-- L1 -->`・`<!-- L2 -->`・`<!-- UI -->` などの目印をつけ、生成時に条件に合わない行を消す。定義は `references/generation.md`
- **理由**: 作らないファイルへのリンクや手順の抜けを、生成時に機械的に防げる
- **不採用**: レベルごとにテンプレートを分ける（共通部分が重複する）。手順に文章で書く（テンプレートとずれる）
- **見直す条件**: 目印が増えてテンプレートが読みにくくなったとき

## D-009 AGENTS.md の禁止事項と、コメント・コミットメッセージの書き方は、ガイドラインと一部重なってよい

- **決定**: 「テストを緩めて通さない」などの数行の禁止事項と、コメント・コミットメッセージの書き方（D-032）は、ガイドラインと重なっても AGENTS.md に残す。それ以外の重複は片方にまとめる
- **理由**: L0 ではガイドラインを入れないため。コメントとコミットメッセージは、判断と進捗の記録をなくしたあとの理由と引き継ぎの置き場所なので、コメントの膨らみや経緯の書き足しをどの構成でも防ぐ

## D-010 変更の範囲を「関係するまとまり」と定義し、継ぎ足さず全体として書き直す

- **決定**: 目的に関係するまとまり（関数・モジュール・節）は変更後の全体として書き直し、関係しないものには触らない。完了前に頭から読み直し、最初からこう書かれていたように読めるか確かめる。原則10・テンプレートの AGENTS.md・ガイドラインに入れる
- **理由**: 修正を重ねると継ぎ足しの跡が積もる（このリポジトリでも起きた）。「変更を最小に」が書き直しまで避ける方向に働いていた
- **不採用**: 経緯の言葉を検出する検査を今入れる（まず手順と評価で足りるか確かめる）
- **見直す条件**: 手順と評価だけでは継ぎ足しが続くとき

## D-011 ガイドラインには、その種類のどのプロジェクトにも当てはまる原則だけを書く

- **決定**: 一部の画面や機能にだけ当てはまるもの（キーボード操作、ダークモードなど）は入れず、必要なプロジェクトがコードや AGENTS.md に置く
- **理由**: 当てはまらない原則はコンテキストを圧迫し、無理に当てはめる誤りも生む
- **不採用**: 「〜の場合は」と条件を付けて残す（関係するかを毎回判断させることになる）
- **見直す条件**: 同じ局所的な決定を多くのプロジェクトで毎回書くようになったとき

## D-012 増え続ける記録（decisions.md・failures.md）は、見出しから関係する項目だけを読ませる

- **状態**: 採用。生成先には decisions.md を作らなくなったので、生成先では failures.md とガイドラインにだけ当てはまる（D-032）
- **決定**: 見出しをそれだけで中身が分かる一文にし、エージェントには要件と、見出しから選んだ項目だけを読ませる。テンプレートとこのリポジトリの両方に入れる
- **理由**: 項目を消さないので増え続け、「読む」という指示のままでは全文が毎回コンテキストに入る
- **不採用**: 判断を1件1ファイルに分ける（一覧を見る手間が増える）
- **見直す条件**: 見出しだけでは関係する項目を選べない失敗が起きたとき。このリポジトリでは約300行を超えたので、1項目を短くした（D-031）

## D-013 SKILL.md は 8,000 バイト以内にし、流れと参照ファイルを読むタイミングだけを書く

- **決定**: `SKILL.md` は 8,000 バイト以内にし、詳しい内容は `references/` に移す。検証では、プロジェクトに合わせて書いた行について「その行がなければエージェントが間違えるか」を確かめる（テンプレートの節は、必要性を skill の側で判断済みなので対象外）
- **理由**: Codex は skill の本文を 8,000 バイトで切る（openai/codex#37463）。日本語は1文字約3バイトで、行数では上限を守れない。自動生成した AGENTS.md は一般論で冗長になりやすい
- **不採用**: 大きさを検査するスクリプト（`wc -c` で足りる）
- **見直す条件**: Codex の上限が変わったとき、上限を超える変更が繰り返されたとき

## D-014 複数の意味に取れる依頼は、解釈を挙げて確認させる。AGENTS.md にはコードを読んでも分からないことだけを書く

- **状態**: 採用（確認の場面と形は D-024 で変えた）
- **決定**: 依頼にない機能・設定・抽象化を足さない。生成時は、コードを読んでも分からないこと（正確なコマンド、真似してはいけない書き方、リポジトリにない決定）だけを書き、規約はコード片で示す。守られない指示は強調で直さず、確実な仕組みに移す
- **理由**: Claude Code のベストプラクティス、andrej-karpathy-skills、GitHub の agents.md 2,500 件の分析で同じ指摘があった
- **不採用**: どんなときも確認させる（小さな作業まで止まる）。エージェントの人格の設定（防ぐ失敗を言えない）
- **見直す条件**: 確認については D-024 を見る

## D-015 試した結果は feedback/ に1回1ファイルで残し、同じ問題が2回出たら skill を直す

- **決定**: skill を試した結果を `feedback/` に1回1ファイルで残し、git には入れない。同じ問題が2回の試行で出たら直す。作成時のツールとモデルは、生成の報告とハーネスを入れるコミットのメッセージに残させる（D-032）
- **理由**: 生成先での改善が skill に戻る道がなかった。記録には試したプロジェクトの中身が入るので公開しない
- **不採用**: 振り返り用の skill を今作る（手順がまだ決まっていない）。記録を言い換えて git に入れる（漏れたときに履歴に残る）
- **見直す条件**: feedback/ を読み切れなくなったとき、振り返りの手順が固まったとき

## D-016 評価役のサブエージェントを L1 から標準で入れ、懐疑的に判定させる

- **決定**: `evaluator` を L1 以上の Claude Code のプロジェクトとこのリポジトリに入れる。「問題があるはず」という前提で確かめ、指摘には根拠と重さ（必ず直す / 直した方がよい）を付け、「必ず直す」の有無で合否を決める。基準は AGENTS.md とガイドラインを正にし、評価役には観点と判定のしかただけを書く。ツールは Read・Grep・Glob・Bash にし、本文でも直さないよう指示する
- **理由**: 作った本人の評価は甘くなる（原則6）。根拠を求めないと確かめずに合格と言い、重さを分けないと直す・確かめるが終わらない。懐疑的に判断させるのはオーナーの要望
- **不採用**: L2 だけに入れる。評価役に完了条件を書き写す（2か所に分かれる）
- **見直す条件**: 指摘が細かすぎて進まない、見逃しが続く、Codex のサブエージェントの書き方を確かめたとき

## D-017 読み取りのコマンドは allow に入れ、.env の抜け道はサンドボックスか置き場所でふさぐ

- **決定**: `allow` に読み取りのコマンドとテスト・lint を引数まで完全な形で入れる。`.env` は `Read(**/.env)`・`Read(**/.env.*)` の `deny` で止め、届かない範囲を agent-tools.md に書く。本物の秘密情報を置くプロジェクトでは、サンドボックスか、秘密情報をプロジェクトの外に置くことを提案する
- **理由**: 評価役が確かめるたびに確認が出ていた。`Read` の `deny` はファイル名を指定しない読み取りには効かない
- **不採用**: `Bash(git diff *)` のような `*` 付きの許可（`--output` で上書き、`--no-index` で `.env` を読めた）。`Read(./.env)`（サブフォルダに効かない）。テンプレートでサンドボックスを常に有効にする（開発のコマンドが動かなくなる）
- **見直す条件**: 権限やサンドボックスの仕様が変わったとき、Codex での止め方を確かめたとき

## D-018 評価する役は、毎回呼ぶ evaluator と、必要なときだけ呼ぶ qa・performance に分ける

- **決定**: evaluator は実装のたびに呼び、コードを読む確認（明らかな性能の問題を含む）とテスト・lint を受け持つ。流れを通して試す qa と、測って目標と比べる performance は必要なときだけ呼ぶ役として framework.md に書く。テンプレートは必要になったときに作る
- **理由**: 毎回の役に操作や測定まで載せると、時間と費用がかかり指摘も細かくなりすぎる
- **見直す条件**: 必要なときだけ呼ぶ役が呼ばれずに見逃すとき

## D-019 評価役には permissionMode: auto を付け、確かめるたびの確認をなくす

- **決定**: 評価役の frontmatter に `permissionMode: auto` を書く。`dontAsk` を使うプロジェクトでは付けない（agent-tools.md）
- **理由**: 許可リストを入れても、評価役はパイプや `cd … &&` を使うので確認が続いた。評価役は書き換えない役で、auto では別のモデルが操作をチェックする
- **不採用**: サンドボックスで確認をなくす（確認を減らすためだけには重い）。`Bash(grep *)` などの広い許可（D-017 の抜け道が開く）
- **見直す条件**: auto の評価役が止めてほしい操作をしたとき、仕様が変わったとき

## D-020 会話を長くしないよう、報告を短くし、依頼の終わりでセッションを変えさせる

- **決定**: テンプレートの AGENTS.md で、報告を結論・未確認・次にやることの順で短く書かせ、依頼の終わりに新しいセッションを勧めて最初に送る一文を添えさせる。依頼の途中で長くなったら、終わったことと残りを短くまとめてから `/compact` などを勧めさせる。評価役の報告は40行程度まで
- **理由**: 最初の試行で会話が膨らんだ。主な原因は読み込み（D-021）だったが、手間なく入れられ膨らむ速さは確実に下がる。progress.md から読み直す方が、長い会話を持ち越すより古い細部を取り違えにくい
- **不採用**: 決まった長さでセッションを変えさせる（エージェントは会話の長さを正確に知れない）
- **見直す条件**: 短い報告で必要な事項が抜けるとき、新しいセッションで引き継ぎが漏れるとき

## D-021 会話を膨らませる読み込みを減らす: 必要な部分だけ読み、探す作業はサブエージェントに任せる

- **決定**: テンプレートの AGENTS.md で、大きなファイルや保存された長い出力は grep や行の範囲で読ませ、複数ファイルをまとめて `cat` させない。decisions.md の見出しは grep で一覧にさせる。CLAUDE.md で、多くのファイルを読んで探す作業と Web の調べものをサブエージェントに任せさせる
- **理由**: 最初の試行の記録を数えると、Bash と Read の出力が3〜5割を占め、保存された出力の丸ごとの読み直し、decisions.md の全文、まとめての `cat` が目立った。Web の調べものは約6%
- **不採用**: 読む大きさを hook で制限する（必要なときに全文を読めなくなる）。最初から入っている約10万トークン（システムの指示、ツールの定義など）を減らす指示（ユーザーの環境の設定で、ハーネスでは変えられない）
- **見直す条件**: 次の試行で読み込みが主な原因にならないとき、サブエージェントの結論の取り違えが起きたとき

## D-022 CLAUDE.md のテンプレートは、生成先と違う名前（claude-instructions.md）で置く

- **決定**: テンプレートの `CLAUDE.md` を `claude-instructions.md` にする。対応は `generation.md` の表に書く。`AGENTS.md` のテンプレートは名前を変えない
- **理由**: Claude Code は読んだファイルのフォルダの `CLAUDE.md` を指示として読み込み、このリポジトリで実際にテンプレートの指示が混ざった
- **不採用**: `AGENTS.md` も名前を変える（Codex で困るかをまだ確かめていない）
- **見直す条件**: Codex でテンプレートの `AGENTS.md` が指示に混ざると確かめたとき

## D-023 block-dangerous.sh は、コマンドの中の位置によらず止め、作業中の変更を捨てる git の操作も止める

- **決定**: パターンをコマンド名の始まり・git のオプション・同じコマンドの中の引数で組み立て、位置によらず止める。`git clean -f`、`git checkout .`・`-f`、`git restore .`、`find … -delete`、`git push origin +main` も止める。`git rm`、`git clean -n`、`git restore --staged` は止めない
- **理由**: `sudo rm -rf`、`xargs rm -rf`、`/bin/rm -rf`、`git -C … push --force` などが通り、逆に後ろのコマンドの `-f` で誤って止まっていた。足した git の操作は作業中の変更を取り戻せない形で消す
- **不採用**: コマンドを構文として解析する（hook には重い。文字列の中に当たる誤検出は残るが、止まってもユーザーに頼めば済む）。テストを今置く（次にパターンを直すときに作る）
- **見直す条件**: 止めるべきでないコマンドで作業が進まないとき、パターンをもう一度直すとき

## D-024 決まった場面では、書き始める前に受け取り方を3〜4行で返させ、返事を待たせる

- **決定**: 依頼が複数の意味に取れる、判断を左右する不明点がある、変更が広いか取り消しにくい、短い依頼に補った前提が多い、の4つの場面で、「受け取った内容／やること（やらないことも）／別の読み方（1つ）／これで進めてよいか」を1項目1行で返させる。迷っていなくても書かせる。小さく取り消しやすい作業は返さず、置いた前提を報告で伝える
- **理由**: オーナーの要望。D-014 の「迷ったら聞く」は、AI が自分で1つに決めたことに気づかないと効かない。最初の案は約10行に膨らんだので、1項目1行で別の読み方を1つに絞った
- **不採用**: hook で毎回確認を差し込む（曖昧かを判断できない）。plan mode を使わせる（重く、Codex にない）
- **見直す条件**: 確認が多すぎる、または返すべき場面で返さずに外す失敗が2回起きたとき

## D-025 Modern Web Guidance は、生成物に組み込まず、勧めもしない

- **決定**: Chrome チームの skill「Modern Web Guidance」を、テンプレートに組み込まず、導入も勧めない
- **理由**: オーナーの判断。外部の skill で中身が速く変わり（原則8）、小さな変更でも呼ばれて読み込みが増えるおそれがある。効果を試していない
- **不採用**: frontend のプロジェクトのときだけ導入を勧める（効果と読み込む量を試していない）
- **見直す条件**: frontend のプロジェクトで、古い Web の書き方をする失敗が繰り返し起きたとき

## D-026 テスト・lint は失敗だけを出す形で書かせ、ガイドラインは見出しから選んだ節だけ読ませる

- **決定**: テスト・lint・型チェックのコマンドを、失敗だけを出し、場所と理由が分かる形で書かせる（警告を隠すオプションは使わない）。ガイドラインは `grep -n "^##" docs/guidelines/*.md` で見出しを一覧にし、関係する節だけを読ませる

- **見直す条件**: 失敗の原因が分からず全体を実行し直すことが続くとき、節だけ読んで別の節の原則を見落としたとき

## D-027 探す作業の Explore と qa は Haiku で動かす

## D-028 生成先の記録は、全員のもの（`docs/`）と一人のもの（`docs/local/`、git に入れない）に分ける

- **状態**: 廃止（→ D-032）。進捗の記録をなくし、失敗の記録には誰にでも起きる失敗だけを書くことにしたので、分ける先がなくなった。「一人の事情を共有の文書に混ぜない」原則はガイドラインに残る
- **決定**: 生成先の progress.md と failures.md を、全員に関わるもの（`docs/`）と一人の作業や環境のもの（`docs/local/`、`.gitignore` に入れる）に分ける。一人で開発していても分ける。振り分けの基準は「誰にでも当てはまるか。迷ったら `docs/local/`」で、テンプレートの AGENTS.md に置く。一人の好みはユーザー設定に置かせる。decisions.md は分けない
- **理由**: オーナーの指摘。共有すると一人に固有の問題が記録に載り、ほかの人のエージェントの動きまで変える。人数で構成を変えないのは、振り分けが毎回同じ基準になり、人が増えても書く先が変わらないため
- **不採用**: 1ファイルの中で分ける（一人の分も git に入る）。各項目に当てはまる範囲を書く（読む量は減らず、判断もエージェント任せ）。共有の記録には PR でだけ入れる（一人の開発では重い）。複数人のときだけ分ける（人が増えたときに移し替えが要る）。decisions.md はプロジェクトとしての判断なので分けない
- **見直す条件**: 振り分けの間違いが続くとき、ツールに個人用の記録の置き場所ができたとき

## D-029 ハーネスの効き目は、evals/ で同じタスクを条件を変えて自動実行し、仕様変更を重ねたときのコードと文書の崩れ方で比べる

- **決定**: `evals/` に、サンプルのプロジェクト・依頼文・隠しテスト・固定した L1 のハーネスをタスクごとに置き、ユーザー設定を切り離した一時フォルダで `claude -p` を実行する。1回目のあとに仕様変更を新しいセッションで続けて頼み、変えた行数、関数の長さ、重複、使われない関数、古い記述、経緯の言葉を数える。同じ条件を3回以上実行し、全回成功したかと指標の幅も見る。確認を求めて止まったら了承を返し（最大2回）、回数を手間として残す。仕組みの詳細は `evals/README.md`
- **理由**: 仕組みを足す案に効く根拠がなかった（原則7）。小さなリポジトリでは成功率に差が出ず、設計の悪さは変更を重ねたときに手間と古い記述として出る。ハーネスは毎回生成せず固定し、生成のばらつきを混ぜない
- **分かったこと**: 成功率と仕様変更の手間には差がない。L1 はコストと時間が約3倍。差は確認の回数と、AGENTS.md に写した決まりが古く残ることに出た（D-030 で直した）。Haiku のコードの形を Sonnet に近づける兆しは、作り直したあとははっきりしない
- **不採用**: `--bare` で設定を切り離す（API キーが要り、ハーネスの hook も止まる）。実際の失敗から20〜50件のタスクを作る（記録にある失敗が少なく、多くは書き方の失敗）。コメントの数を数える（多さで良し悪しが決まらない）
- **まだ作っていないもの**: オーナーのガイドラインに照らした主観的な品質の採点。部品を1つずつ外して比べること
- **見直す条件**: 大きなリポジトリのタスクでも指標に差が出ないとき、`claude -p` の出力や設定を切り離すオプションが変わったとき

## D-030 生成する AGENTS.md には仕様の決まりの中身を写さず、文書の場所と読むきっかけだけを書かせる

- **状態**: 採用（evals で確かめた段階。実際のプロジェクトでは未確認）
- **決定**: 仕様の決まりが文書にあるとき、AGENTS.md には中身を写さず、場所と読むきっかけだけを書かせる。書き方の規約に見えても決まりから来る中身は写さない。頼まれた仕様変更では先に文書を直してから実装させる。評価役に、古い値や言葉で grep して古い記述が残っていないかを確かめる観点を足す
- **理由**: evals で、L1 が AGENTS.md に写した決まりを古いまま残し、頼まれた仕様変更でも確認を求めていた。ハーネスなしでも毎回 `docs/pricing.md` を読んで成功していたので、写さなくても失敗は増えないと見た。直したあと、AGENTS.md の古い記述は0回になり、Sonnet の確認もなくなった
- **不採用**: 仕様を変えたら AGENTS.md も直す手順を足す（2か所に書くことは変わらない）
- **見直す条件**: 文書を読まずに決まりを間違えることが続くとき

## D-031 このリポジトリの記録は短く保つ: decisions.md は1項目数行、progress.md に済んだことを書かない

- **決定**: decisions.md の1項目は、決定・理由の要点・主な不採用案・見直す条件の数行にし、調べた経緯や測った数字はコミットメッセージに書く。progress.md には済んだ作業を書かず、進行中・次にやること・注意だけにする
- **理由**: decisions.md が約69KB、progress.md が約10KB になり、読むたびにトークンを使っていた。progress.md の「進行中」は済んだ作業の履歴になり、D-005 から外れていた。経緯は git の履歴で追える
- **不採用**: 2つとも消す（判断の理由がなくなり、決めたことをまた議論し直す）。廃止・対策済みの項目を別ファイルに移す（廃止の項目はまだ少なく、採用中の項目が長いことが原因だった）。判断を1件1ファイルに分ける（D-012 と同じ理由）
- **見直す条件**: 理由が短すぎて、判断をまた議論し直すことが起きたとき

## D-032 生成先には判断と進捗の記録を作らず、AGENTS.md の「どこに何があるか」と git で引き継がせる

- **決定**: テンプレートから decisions.md と progress.md を消す。要件（目的・扱わない範囲・用語）は AGENTS.md の概要に、構成は AGENTS.md の新しい節「どこに何があるか」（フォルダ単位で、grep では分からない受け持ち・正となる場所・依存の向き・仕様の文書。10〜15行まで）に書かせる。今の状態は git の状態とコミットメッセージ（理由・主な不採用案・残りの作業）で引き継ぐ。その場所だけの理由はコードのそばのコメントに、今の理由だけを書かせる。失敗の記録は残し、1件2行にする。ガイドライン4つと原則（状態の引き継ぎ、1つを正にする、不採用案を残す）も合わせて直した（オーナーの確認済み）
- **理由**: オーナーの指摘。判断と進み具合はコードとコミットメッセージにだいたいあり、別に書くと二重になって古くなる（evals で、写した決まりが古く残った）。evals ではハーネスがなくても仕様の文書を探して読めており、成功率は同じでコストは約3倍だった。失敗の記録は、同じ失敗が2回目かをセッションをまたいで判断する手がかりがほかにないので残す
- **分かったこと**: evals で記録ありの L1 と比べ、成功は変わらず、コストは少し下がり、Haiku の確認の回数が減った。新しいモジュールを作った2回は、2回とも同じ依頼で「どこに何があるか」を直した。古い記述と経緯の言葉はどちらも0。ただし evals ではエージェントがコミットしないので、コミットメッセージでの引き継ぎは確かめられていない
- **不採用**: コードのファイルを1つずつ並べた地図（移動や改名のたびに古くなり、行数も増える）。失敗の記録も消す（2回目の判断ができなくなる）。このリポジトリの記録も同時に消す（このリポジトリは skill の設計そのものが成果物で、生成先で効いてから合わせる）
- **見直す条件**: 生成先で、判断の理由が見つからず一度やめた案に戻す失敗や、セッションをまたいで残りの作業を取りこぼす失敗が起きたとき

## D-033 まだ実行できないコマンドは「（未確認）」を付けて AGENTS.md に書き、`allow` には確かめてから足す

- **決定**: 依存を入れる前などで実行できないコマンドは、推測した形に「（未確認）」を付けて書く。入口がまだないもの（起動など）は「決めたらここに書く」とする。使わない検証（型チェックのない言語など）は行から外し、「完了の条件」はテンプレートの段階から「『コマンド』に書いた検証」を指す形にする。未確認のコマンドは `allow` に入れず、印を消すときに足すことを生成先の `CLAUDE.md` に書く
- **理由**: 空のフォルダでの生成で、「確かめてから書く」と「未確認と書いてよい」が4つのファイルで食い違い、生成役が迷った。確かめると形が変わることが多く、先に `allow` に入れると使われない許可や思わない形の許可が残る
- **不採用**: 確かめられるまでコマンドを書かない（次のセッションが毎回探すことになる）。足す手順を生成時の報告にだけ書く（報告は残らず、次のセッションに伝わらない）
- **見直す条件**: 「（未確認）」の印が確かめられないまま残り続ける失敗が起きたとき

## D-034 AGENTS.md とガイドラインの重なりは AGENTS.md に残し、ガイドラインの当てはまらない節は目印で消す

- **決定**: 「継ぎ足さず全体を書き直す」「仕様を変えるときは文書を先に直す」「一人の事情は共有の文書に書かない」など、AGENTS.md の作業ルールと同じことをガイドラインから消す。コメントとコミットメッセージの書き方は、AGENTS.md とガイドライン1つの2か所までにする。画面の話（ショートカットの一覧、状態を共有する範囲）は design.md から ui.md に移す。coding.md の「保存するデータ」「時間のかかる処理」に `<!-- DATA -->`・`<!-- UI|SERVER -->` を付け、当てはまらなければ節ごと消す（オーナーの確認済み）
- **理由**: AGENTS.md の作業ルールは L0 にも入り毎回読まれるので、ガイドライン側の同じ行はどのレベルでも二重になる（D-009 の「それ以外の重複は片方にまとめる」）。丸ごとコピーすると、画面も保存データもないプロジェクトに使わない節が残る
- **不採用**: ガイドラインの側を残して AGENTS.md から消す（L0 で抜け、見出しで選ばれないと読まれない）。当てはまらない節を持つガイドラインをファイルに分ける（ファイルが増える）
- **見直す条件**: 人がガイドラインだけを読んで、作業ルールが抜けて見える失敗が起きたとき。目印が増えてガイドラインが読みにくくなったとき

## D-035 目標のファイル（docs/goal.md）は、L2 か大枠を残したいときだけ作る

- **決定**: オーナーの意思としての目標（一言でいうと、なぜ作るか、完成の条件、扱わない範囲、優先順位）を `docs/goal.md` に書く。作るのは L2 か、オーナーが大枠を数行以上で残したいと言ったときだけ。エージェントは書き換えず提案する。作ったら AGENTS.md の概要の「扱わない範囲」を消し、リンクに置き換える（`<!-- GOAL -->`）。マイルストーンと「いまここ」は書かない（オーナーの確認済み）
- **理由**: 目標はコードから分からず、あまり変わらないので、進捗の記録のように二重になって古くなりにくい。長い自律作業では、完成の条件と優先順位がないと、目の前のタスクを磨き続けたり範囲の外へ広げたりする。エージェントが育てる AGENTS.md に混ぜると、オーナーの意思まで書き換えられる。どちらもまだ観察していない、予想される失敗
- **不採用**: どのプロジェクトにも作る（小さなプロジェクトでは AGENTS.md の概要と二重になり、防ぐ失敗も言えない）。AGENTS.md の概要を長くする（約100行を圧迫し、オーナーの意思と混ざる）。マイルストーンも入れる（このリポジトリの vision.md で「いまここ」が古くなった）
- **見直す条件**: 生成先で目標のファイルが読まれない、または古くなる失敗が起きたとき。長い自律作業のタスクを evals に作り、効き目が見えなかったとき

## D-036 生成するファイルが日本語で yomiyasu が使えるときだけ、人が読むファイルを yomiyasu で推敲し、生成先にも推敲の指示を置く

- **決定**: 生成するファイルが日本語で、使えるスキルの一覧に yomiyasu（外部の、AI が書いた日本語を推敲するスキル）があるときは、生成した `README.md` と `docs/goal.md` を yomiyasu で推敲する。エージェント向けのファイルは推敲しない。生成先で使い続けるための指示の行は、yomiyasu がプロジェクトの中で git に共有されていれば `AGENTS.md` に（`<!-- YOMIYASU -->`）、利用者のフォルダにだけあればその人のユーザー設定に置く。ユーザー設定に指示がなければ、足すことを生成の報告で勧める（オーナーの依頼）
- **理由**: 外部のものを生成物に組み込まない D-025 と違い、オーナーが選び、ない環境では何もしない。AI が書いた日本語には不自然な比喩や主語のあいまいさが残りやすく、人が読むファイルでは読みにくさになる。yomiyasu は名前を出すか指示のファイルで求めないと読まれないので、行がないと生成先では使われない。利用者のフォルダに入れたスキルはどのプロジェクトでもその人だけが使えるので、指示も同じ範囲に効くユーザー設定にそろえる
- **不採用**: 条件を付けずに入れる（日本語でない、yomiyasu がないプロジェクトに使わない行が残る）。利用者のフォルダにだけあるときも `AGENTS.md` に入れ、設計の合意で確かめる（ほかの人には効かず、ユーザー設定と重なる。毎回の確認も増える）。一人だけの、このプロジェクトだけの指示を置く `AGENTS.local.md`（git に入れず、`AGENTS.md` の冒頭で読ませる）を作る（yomiyasu はプロジェクトごとに分ける必要がなく、ほかに要る場面もまだない。使わない生成先にも読む文と `.gitignore` の行が入る）。ガイドラインに書く（ガイドラインはオーナーの原則を元にしていて、特定の外部スキルの話は合わない）。エージェント向けのファイルも推敲する（指示の言い回しが変わり、効き目が測れなくなる）
- **見直す条件**: yomiyasu の名前や呼ばれる条件が変わったとき。推敲で README の意味が変わる失敗が起きたとき。一人だけの、このプロジェクトだけの指示が要る場面が出たとき（`AGENTS.local.md` を考え直す）
