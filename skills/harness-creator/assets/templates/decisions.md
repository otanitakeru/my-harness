# 設計判断の記録

要件と、**なぜそうしたか** を残す。原則（どう決めるか）は `docs/guidelines/` にあり、ここにはこのプロジェクトでの具体的な決定を書く。
古い判断は消さず、状態を「廃止」にして、やめた理由を書く。
判断は全部を読まず、見出しから関係するものを選んで読む。そのため見出しは、それだけで何を決めたかが分かる一文にする。

- **利用者**: <!-- PROJECT: 誰が使うか -->
- **扱わない範囲**: <!-- PROJECT: 今はやらないこと -->
- **用語**: <!-- PROJECT: プロジェクト固有の用語と意味。なければ行ごと消す -->

     docs/guidelines/ の原則から外れる判断も1件として書き、どの原則から外れるかを「理由」に書く -->


### D-001 <!-- PROJECT: 何を決めたかが分かる一文（例: API の入力はスキーマで検証し、内部には検証済みの型だけを渡す） -->

- **日付**: YYYY-MM-DD
- **状態**: 採用 / 廃止（→ D-xxx）
- **決定**: 何をどう決めたか
- **理由**: なぜそうしたか
- **不採用案**: 検討して採らなかった案と、その理由
- **見直す条件**: どの前提が変わったら見直すか
