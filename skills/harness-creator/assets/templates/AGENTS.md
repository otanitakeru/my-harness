## 作業の進め方

### 開始時
- `docs/progress.md` と `git log --oneline -20`、`git status` を読み、今の状態を把握する <!-- L1 -->
- `./init.sh` を実行して開発環境を起動する <!-- L2 -->
- テストやアプリを一度動かし、作業前の時点で壊れていないか確認する。壊れていたら、新しい作業より先に報告する

### 着手前
- 期待する挙動・今回扱わない範囲・確認方法を明確にする
- 次のときは、書き始める前に自分の受け取り方を返し、返事を待つ: 依頼が複数の意味に取れる、判断を左右する不明点がある、変更が広いか取り消しにくい（多くのファイル、設計や公開の形、削除・移動）、短い依頼に自分で補った前提が多い。迷っていなくても書く。書いて見せると、自分では気づかない読み違いが見えるため。次の4行だけにし、例や理由は足さない
  - 受け取った内容: …
  - やること: …（やらないことも、ひと言で）
  - 別の読み方: …（いちばんありそうな1つ。思い当たらなければこの行は書かない）
  - これで進めてよいですか？
- 誤字の修正や、言われたとおりの1か所の変更など、小さく取り消しやすい作業は返さずに進めてよい。置いた前提は報告で伝える
- 変更が入るまとまり（関数・モジュール・ドキュメントの節）を特定し、変更後にそのまとまりがどういう形になるかを考えてから書き始める
- 依頼が `docs/decisions.md` の方針とぶつかるときや、もっと良い案があるときは、実装の前に懸念と代案を出す <!-- L1 -->
- データモデルや設計方針に関わる変更は、実装より先に `docs/decisions.md` を直す <!-- L1 -->

### 作業中
- 変更するのは、目的に関係するまとまりだけ。関係しないもの（無関係な整形・改名・依存更新・リファクタリング）には触らず、既存の作業中の変更も消さない
- 関係するまとまりは、継ぎ足さずに変更後の全体として書き直す。最初からその仕様だったかのような形にし、変更の経緯はコードやコメントに残さない
- 局所的な修正でも、全体の規約（型・命名・層の分け方・共通化の基準）に合わせる
- 依頼にない機能・設定項目・抽象化は足さない。依頼の範囲外に改善点を見つけても、その場では変更せず提案に留める
- 読むのは必要な部分だけにする。大きなファイルや、長すぎて別のファイルに保存されたコマンドの出力は、grep や行の範囲を指定して読み、丸ごと読み直さない。複数のファイルをまとめて `cat` しない。読んだものはすべて会話に残り、作業のあいだ膨らみ続けるため
- 長い作業では、きりのよいところで `docs/progress.md` を今の状態に書き換え、会話がいつ圧縮されても再開できるようにする。依頼の途中で会話が長くなったら、書き換えてから、会話を要約して続けるコマンド（Claude Code の `/compact` など）を使うよう勧める <!-- L1 -->

### 完了の条件
- 成功条件を満たしていることを、テスト・lint・型チェックの実行結果で確認する
- UI の変更は、実際に画面を操作して確認する <!-- UI -->
- 変更したまとまりを、差分ではなく頭から読み直し、前の版を知らない人が読んでも最初からこう書かれていたように見えるか確かめる。意図しない変更が入っていないかは差分で確かめる
- 報告は短く、結論（何ができて今どういう状態か、1〜2行）→ **未確認の事項**と失敗した確認 → 次にやること（ユーザーの判断や作業が要るものを先に）の順で書く。確認していないことを「動きます」と書かない。通った確認と作業の細目は一言にまとめ、差分・コミット・`docs/` を指す。長い報告は読まれず、会話も膨らむため

### 終了時
- `docs/progress.md` を今の状態に **書き換える**（追記しない） <!-- L1 -->
- 依頼が終わったら、次の依頼は新しいセッションで始めるよう伝え、最初に送る一文（例: 「progress.md の次にやることの1から始めて」）を添える。続きは `docs/` から読み直せるので、長い会話を持ち越すより古い細部を取り違えにくい <!-- L1 -->
- 後から理由が必要になる判断は、`docs/decisions.md` に残す（不採用案とその理由も） <!-- L1 -->
- 自分の失敗に気づいた・指摘されたときは、`docs/failures.md` に書く <!-- L1 -->

## タスク一覧の使い方 <!-- L2 -->

- 1回のセッションでは、`feature_list.json` から `passes` が `false` の項目を1つだけ選んで進める
- `passes` を `true` にするのは、`steps` のとおりに実際に操作して確かめた後だけ
- 変更してよいのは `passes` だけ。項目の削除や、`description`・`steps` の書き換えはしない。おかしい項目は報告する

## 承認が必要な操作

次の操作は、対象・影響範囲・復旧方法を示し、明示的な承認を得てから行う。開発・テストでも、接続先が破棄してよい環境かを確かめる。

- データの削除・初期化・上書き
- 取り消しの難しい git 操作（`git push --force`, `git reset --hard` など）やファイルの再帰的な削除
- 本番環境への操作、外部への送信

## 禁止事項

- テストを削除・無効化・緩めて通すこと
- 失敗を握りつぶすこと（空の catch、エラーの無視）
- 秘密情報や実在の個人情報を、コード・ログ・コミット・テストデータに含めること

## このファイルの育て方

- エージェントが同じミスを2回したら、防止策を入れる。置き場所の選び方は `docs/failures.md` にある <!-- L1 -->
- ルールを足すときは、末尾に足さず、既存の節のどこに入るかを考えて書き直す
- 約100行を超えたら、詳しい内容を `docs/` に分け、ここにはリンクだけ残す
