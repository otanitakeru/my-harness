# ガイドライン: ドキュメント

プロジェクトをまたいで使う、ドキュメントの書き方の原則。「どう決めるか」だけを書く。
このプロジェクトでの具体的な決定は `docs/decisions.md` に書く。原則に合わない判断をするときも、理由を `docs/decisions.md` に残す。

## 置き場所を役割で分ける

| 種類 | 置き場所 | 書くこと |
|---|---|---|
| 概要 | `README.md` | 概要・起動方法・ほかのドキュメントへの案内だけ |
| 設計判断の記録 | `docs/decisions.md` | 要件と、**なぜそうしたか**（理由・採らなかった案・やめた方針） |
| 原則 | `docs/guidelines/` | プロジェクトをまたいで使う「どう決めるか」の原則（このファイルなど） |
| 今の状態 | `docs/progress.md` | 作業の引き継ぎ（進行中・次にやること・注意）。履歴は持たず、毎回書き換える |
| 失敗の記録 | `docs/failures.md` | AI エージェントの失敗と、入れた対策 |
| 利用者向けの説明 | `docs/usage.md` など | **何ができて、どう操作するか** |
| AI エージェントへの指示 | `AGENTS.md` | 作業の進め方のルール。`CLAUDE.md` は `@AGENTS.md` で読み込むだけ |

- 同じ内容を2か所に書かない。片方だけ直されて食い違うため。必要なら片方からもう片方へリンクする
- AI エージェントへの指示はツールごとに書き分けず、1つのファイルを正にして、ほかはそれを参照する
- 設計判断の記録と今の状態を混ぜない。今の状態は書き換えていくが、判断は後から参照されるため

## 書き直し方

- ドキュメントもコードと同じく、変更後の全体として書き直す。節・注記・例外を末尾に足す前に、既存の構成のどこに入るかを考える。後から足した順に並んだ文書は、読む人が全体の構成をつかめないため
- 作業の経緯（何をいつ変えたか）は git の履歴に任せ、ドキュメントに書き写さない。経緯が必要な判断は、設計判断の記録に書く

## 設計判断の書き方

- 後から理由を知る必要がある重要な判断について、決定と理由を残す。前提が変わったときに見直せるようにするため
- **主な不採用案と、その理由も残す**。同じ案を何度も検討し直したり、AI が良かれと思って戻したりするのを防ぐため
- 方針を変えたときは、前の方針とやめた理由を残す。古い判断は消さず「廃止」にする
- データモデルや設計方針に関わる変更は、実装より先に記録を直す

## 利用者向けの説明

- 利用者から見える挙動を変えたら、同じ変更（コミット・PR）で説明も直す。古い説明が正しいものとして読まれるため
- 画面の文言は、言い換えずに画面の表示どおりに書く
- スクリーンショットは、撮る条件と手順を決め、できればスクリプトで撮り直せるようにする。手で撮った画像は、撮り直しの漏れが起きやすいため
