# ガイドライン: ドキュメント

プロジェクトをまたいで使う、ドキュメントの書き方の原則。「どう決めるか」だけを書く。
このプロジェクトでの具体的な決定は、コードと設定そのもの、`AGENTS.md`、仕様の文書に置く。原則に合わない判断をするときは、その箇所のコメントかコミットメッセージに理由を残す。

## 置き場所を役割で分ける

| 種類 | 置き場所 | 書くこと |
|---|---|---|
| 概要 | `README.md` | 概要・起動方法・ほかのドキュメントへの案内だけ |
| AI エージェントへの指示 | `AGENTS.md` | 概要と扱わない範囲、どこに何があるか、作業の進め方のルール。`CLAUDE.md` は `@AGENTS.md` で読み込むだけ |
| 仕様 | `docs/` の仕様の文書 | コードを読んでも分からない決まり（計算のしかた、表示の形など） |
| 原則 | `docs/guidelines/` | プロジェクトをまたいで使う「どう決めるか」の原則（このファイルなど） |
| 失敗の記録 | `docs/failures.md` | AI エージェントが繰り返した失敗と、入れた対策 |
| 利用者向けの説明 | `docs/usage.md` など | **何ができて、どう操作するか** |
| 判断の理由と経緯 | コードのコメント、コミットメッセージ | 下の「判断の理由の残し方」 |

- 同じ内容を2か所に書かない。片方だけ直されて食い違うため。必要なら片方からもう片方へリンクする
- コードと設定を読めば分かることは、文書に書き写さない。文書は書き写した分だけ古くなるため
- AI エージェントへの指示はツールごとに書き分けず、1つのファイルを正にして、ほかはそれを参照する
- 共有するドキュメントには、そのリポジトリで作業する誰にでも当てはまることだけを書く。共有するドキュメントは全員が読み、AI エージェントは指示として従うので、一人の事情が混ざると、ほかの人の作業まで変わるため

## 書き直し方

- ドキュメントもコードと同じく、変更後の全体として書き直す。節・注記・例外を末尾に足す前に、既存の構成のどこに入るかを考える。後から足した順に並んだ文書は、読む人が全体の構成をつかめないため
- 作業の経緯（何をいつ変えたか）は git の履歴に任せ、ドキュメントやコメントに書き写さない

## 判断の理由の残し方

- その場所だけに関わる理由（なぜこの形か、採らなかった書き方）は、そのコードのそばに短いコメントで書く。コメントには今のコードの理由だけを書き、前の方針や経緯は書かない。コードを変えたら、コメントも今の理由に書き直す。経緯を書き足していくと、コメントが膨らみ、古い理由が残るため
- 変更の理由は、コミットメッセージに書く。後から理由を知る必要がある判断は、前提が変わったときに見直せるよう、決めたことと理由を書く
- **主な不採用案と、その理由も残す**。同じ案を何度も検討し直したり、AI が良かれと思って戻したりするのを防ぐため
- 仕様・データモデル・設計方針に関わる変更は、実装より先に、それを書いた仕様の文書を直す

## 利用者向けの説明

- 利用者から見える挙動を変えたら、同じ変更（コミット・PR）で説明も直す。古い説明が正しいものとして読まれるため
- 画面の文言は、言い換えずに画面の表示どおりに書く
- スクリーンショットは、撮る条件と手順を決め、できればスクリプトで撮り直せるようにする。手で撮った画像は、撮り直しの漏れが起きやすいため
