# ガイドライン: UI と配色

プロジェクトをまたいで使う、UI と配色の原則。「どう決めるか」だけを書く。
このプロジェクトでの具体的な決定（色や余白の定義、画面構成など）は `docs/decisions.md` に書く。

## 表示するもの

- 最初に出すのは、操作に必要な情報だけ。説明文・ヘルプ・ツールチップは、必要になるまで足さない
- 文言は、機能がひと目で分かる最小限にする。長い文章・小さい文字は避ける
- 説明文で補う前に、並べ方や余白など見た目で関係が分かるようにできないかを考える
- 表示を増やす代わりに、既存の要素の状態で表せないかを考える

## 見た目の統一

- 余白・文字サイズ・フォントは、決めておいた少数の値から選び、画面全体で揃える。特別な理由があるときだけ外し、その理由を `docs/decisions.md` に残す。場所ごとに値が違うと、どれが同じ種類のものかが読み取れなくなるため
- 余白は空けすぎない。関係の近いもの同士は近く、別のまとまりとは離す、という関係を示す分だけ空ける
- カードや枠線で囲むのは、余白と並べ方だけではまとまりを示せないときだけにする。枠の中に枠を重ねない。枠が多いと、どれが大事なまとまりかが分からなくなるため
- 色・余白・文字サイズ・フォントは**意味の名前**で1か所に定義し、コードの中に値を直接書かない。変えるときに1か所で済み、何のための値かがコードから読み取れるため

## 設定

- 設定項目は増やさない。固定値で困らないものは設定にしない
- **同じものを変える場所を2つ作らない**。どこで変えたかが分からなくなるため

## 操作

- 作業中の状態（選択・表示位置・入力途中の内容）を失わせない
- 操作方法は、プラットフォームの慣習に従う
- 確認は、操作の影響が大きく、取り消しが難しいときに出す。毎回出すと、読まずに進めるようになるため
- 時間のかかる処理は、進み具合を見せ、安全に中止できる場合は中止手段を用意する。進み具合が分からない間も、動いていることが分かるようにする
- 処理中は、結果とぶつかる操作だけを止める。結果に影響しない操作（表示の移動など）は止めない

## エラーの見せ方

- 誤りは、作業が無駄になる前に知らせる（入力を始める前、送信の前など）
- エラーは、原因の場所（入力欄・対象の項目）の近くに出す。画面全体を止めるのは、作業を続けられないときだけにする
- エラーが起きても、入力した内容や作業中の状態を消さない。直して、そのままやり直せるようにする
- 再試行で直る失敗（通信の失敗など）には、再試行の手段を用意する
- 文言は「何が起きたか」「どうすればよいか」が分かるようにする。文言の決め方とエラーの種類の分け方は [coding.md](coding.md) の「エラー処理」に従う

## 配色

配色は、情報の優先順位や操作・状態の違いが伝わるように決める。

### 状態の色

- 同じ意味には一貫した表現を使う。状態を足すときは、既存の状態と見分けられるか確かめる
- 状態が重なったときに、どちらの色を優先するかを決めて記録する
- 状態の変化を知らせる表示はなめらかに変え、点滅させない

### 見分けやすさ

- 色だけで状態を区別しない。形・線の種類・文字・アイコンのどれかを併用する（色覚の多様性のため。特に赤と緑だけで分けない）
- 文字と背景のコントラストは WCAG の基準を満たす（本文は 4.5:1 以上）
- 色を決めたら、色覚のシミュレーションで確かめる
