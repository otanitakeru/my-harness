# ハーネスの枠組み

どんなハーネスを作るかを決めるための枠組み。「部品」→「レベル」→「ガイドライン」の順に決め、使い始めてからは「失敗と対策の置き場所」と「見直すタイミング」で育てる。
判断の根拠は [principles.md](principles.md)、ツールごとの書き方は [agent-tools.md](agent-tools.md) にある。

## 1. ハーネスを構成する部品

| # | 部品 | 役割 | 主な実体 |
|---|---|---|---|
| 1 | **地図（指示）** | プロジェクトの概要、ルール、詳しい情報の場所を伝える | `AGENTS.md`（Claude Code では `CLAUDE.md` から読み込む） |
| 2 | **知識** | 要件と判断の理由、どう決めるかの原則を残す | `docs/decisions.md`, `docs/guidelines/` |
| 3 | **状態の引き継ぎ** | セッションが変わっても途中から再開できるようにする | `docs/progress.md`（今の状態だけ）, `feature_list.json`, git の履歴 |
| 4 | **検証手段** | エージェントが自分で正しさを確かめる | テスト, lint, 型チェック, ブラウザ操作（Playwright MCP など）, ログ参照 |
| 5 | **強制（決定的な制御）** | 必ず守るべきことを仕組みで守らせる | CI, pre-commit, 独自 lint, hooks（`scripts/hooks/`） |
| 6 | **手順の再利用** | よくある作業の手順を型にする | skills, スラッシュコマンド |
| 7 | **役割の分離** | 作る役と評価する役を分ける、コンテキストを分ける | サブエージェント |
| 8 | **ガードレール** | 危険な操作を防ぐ | hook での停止, 権限設定, サンドボックス |
| 9 | **外部接続** | 外部サービスやツールにつなぐ | MCP サーバー |
| 10 | **定期メンテナンス** | ドキュメントの鮮度、コードの乱れ、継ぎ足しを定期的に直す | スケジュール実行のエージェント、長い修正の後の書き直し |

## 2. レベルの決め方

プロジェクトの規模と、エージェントにどこまで任せるかで決める。迷ったら1つ下のレベルを選ぶ。

| レベル | こんなとき | 入れる部品 |
|---|---|---|
| **L0: 最小** | 小さなスクリプト、試作、短期間のプロジェクト | 1 地図, 4 検証コマンドの記載 |
| **L1: 標準** | 継続して開発するプロジェクト。エージェントに実装まで任せる | L0 + 2 知識, 3 今の状態と失敗の記録（`failures.md`）, 5 hooks（危険なコマンドの停止、formatter）, 7 評価役のサブエージェント, 8 権限設定（秘密情報のファイル） |
| **L2: 自律** | 長時間の自律作業、複数セッションにまたがる大きな機能、複数エージェント | L1 + 3 タスク一覧と起動スクリプト（`init.sh`）, 4 E2E 検証, 6 skills, 10 定期メンテナンス |

部品9（MCP）は、レベルに関係なく必要なときだけ入れる。

### 評価する役の分け方

評価する役は、毎回呼ぶものと、必要なときだけ呼ぶものに分ける。毎回呼ぶ役に重い確認まで載せると、時間と費用がかかり、指摘も細かくなりすぎるため。

| 役 | いつ呼ぶか | 確かめること | 入れる条件 |
|---|---|---|---|
| **evaluator** | 実装のたびに毎回 | コードを読んで確かめる（明らかな性能の問題も含む）。手元でテスト・lint を実行する | L1 以上 |
| **qa** | 画面や機能をまとめて変えたとき、リリースの前 | 利用者と同じように実際に操作し、正常な流れを通しで試し、変な入力・戻る・やり直す操作・エラーの出方を確かめる | 画面や API があり、操作して確かめる手段がある |
| **performance** | 性能に関わる変更をしたとき、リリースの前 | 測るコマンドを実行し、`docs/decisions.md` の目標や前回の結果と比べる | 性能の目標と、測るコマンドがある |

必要なときだけ呼ぶ役は、いつ呼ぶかが曖昧だと使われない。試す流れや測るものはプロジェクトごとに違うので、テンプレートは用意せず、入れると決めたプロジェクトで作る（作り方は [generation.md](generation.md)）。

### プロジェクトの特徴による追加

| 特徴 | 追加を検討するもの |
|---|---|
| UI がある（Web / アプリ） | 画面を操作して確かめる手段（Playwright MCP、シミュレーターなど）、`guidelines/ui.md`、qa 役 |
| 利用者や外部から呼ばれる API がある | API を通しで呼んで確かめる E2E テスト、qa 役 |
| 性能の目標がある | 目標を `docs/decisions.md` に書く、測るコマンド、performance 役 |
| 利用者向けの説明がある | 挙動を変えたら説明も同じ変更で直すルール、スクリーンショットを撮り直すスクリプト |
| DB やマイグレーションがある | 破壊的なコマンドを `block-dangerous.sh` に追加、マイグレーション手順の明記 |
| 外部 API・課金が絡む | 本番キーを使わせない仕組み、テスト用の設定 |
| アーキテクチャのレイヤーが明確 | 依存方向を検査する lint・構造テスト |
| 複数人で開発する | ドキュメントの置き場所と書き方のルール、PR の流れ |
| 長時間の作業が多い | タスク一覧、開始・終了時の手順の固定 |

## 3. ガイドラインの選び方

`assets/templates/guidelines/` には、プロジェクトをまたいで使う「どう決めるか」の原則がある。L1 以上で、当てはまるものだけを `docs/guidelines/` にコピーし、入れなかったものは理由を設計の合意時に伝える。ガイドラインは書き換えず、プロジェクトでの決定と、原則から外れる判断は `docs/decisions.md` に書く。

| ファイル | 入れる条件 |
|---|---|
| `documentation.md` | 常に（ドキュメントの置き場所の約束を決めるため） |
| `design.md` | モジュールや層を分けるほどのコードがある |
| `coding.md` | コードを書くプロジェクト |
| `ui.md` | 画面がある（Web、デスクトップ、モバイル、TUI など）。配色も含む |

## 4. 失敗の種類と対策の置き場所

エージェントが失敗したら、次の表で対策の置き場所を決める。上ほど確実だが、作る手間がかかる。機械的に検査できるものは文章に書くだけで済ませず、エラーメッセージには直し方を書く。hook と権限設定はそのエージェントを使っているときにしか効かず、ツールを使わない書き換えもすり抜けるため、どのツールにも効かせたいものは pre-commit と CI に置く。

| 置き場所 | 向いている失敗 | 例 |
|---|---|---|
| **CI・lint・テスト** | コードの規約違反、構造の崩れ | 依存方向の違反、命名規則、ファイルサイズ超過 |
| **pre-commit** | コミット前に揃っていればよいもの。人間・どのツールにも効かせたいもの | formatter、lint、秘密情報の検出 |
| **hook** | 実行前に止めたいもの、エージェントにすぐ結果を返したいもの | 危険なコマンドの停止、編集直後の整形・lint 結果 |
| **権限設定** | 読ませたくないファイル、使わせたくないツール | `.env` の読み取り |
| **skill・コマンド** | 手順が長く、順番を間違えやすい作業 | リリース手順、新しい API の追加手順 |
| **サブエージェント** | 自己評価が甘くなる作業 | コードレビュー、UI の品質チェック、継ぎ足しになっていないかの確認 |
| **AGENTS.md・docs** | 判断が必要で、機械的に検査できないこと | 設計の方針、優先順位、迷ったときの判断基準 |

## 5. 部品を見直すタイミング

生成先の `docs/failures.md` に記録された失敗を見て判断する。

- 同じ失敗が2回起きたとき → 部品を足す
- 部品があるのに失敗が続くとき → 部品の置き場所を表の上の段（より確実な方）に移す。指示に「重要」「必ず」などの強調を足して直そうとしない（強調しても守られるようにはならないため）
- モデルを新しくしたとき → 各部品が「何ができない前提」で入っているかを、`failures.md` の「見直す条件」と合わせて見直し、不要なら削る。モデルごとの指示ファイルは作らず、指示は行動で書く
- 同じファイルに何度も手を入れたとき → そのファイルを全体として読み直し、継ぎ足しの跡があればまとめ直す
