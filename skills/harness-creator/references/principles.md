# ハーネスの設計原則

ハーネスに何かを追加・変更するときの判断基準。この skill の手順（SKILL.md）と枠組み（[framework.md](framework.md)）は、この原則に基づく。
プロジェクトのコードの原則は `assets/templates/guidelines/` にあり、こちらとは別。
主な出典: OpenAI「Harness engineering」、Anthropic「Effective harnesses for long-running agents」「Harness design for long-running apps」。

## 1. エージェントが見えないものは存在しない
知識・計画・状態・判断理由は、すべてリポジトリ内のファイルに置く。チャットや頭の中だけにある情報は、次のセッションでは失われる。

## 2. AGENTS.md は地図であって、マニュアルではない
入口のファイルは約100行に抑え、詳しい内容へのリンクを並べる。全部を1ファイルに詰めると、コンテキストを圧迫し、更新もされなくなる。

## 3. 確かめる手段を渡す
テスト、型チェック、lint、ブラウザ操作、ログの参照など、エージェントが自分で正しさを確認できる手段を用意する。「完了」は自己申告ではなく、検証結果で判断する。

## 4. ミスは仕組みで潰す
毎回守るべきことは、文章で頼むのではなく CI・pre-commit・hook・lint で強制する。同じミスが2回起きたら、より確実な仕組みに反映する。エラーメッセージには直し方を書き、そのままエージェントの次の行動につながるようにする。

## 5. 状態はファイルで、今の分だけ引き継ぐ
今の状態（progress.md）、タスク一覧（壊されにくい JSON）、git の履歴で、セッションが変わっても途中から再開できるようにする。今の状態は区切りごとに書き換え、会話がいつ圧縮されても困らないようにする。時系列の作業履歴は書かない。経緯は git の履歴にあり、二重に書くと長くなって読まれなくなるため。

## 6. 作る役と評価する役を分ける
自分が書いたものを自分で評価すると甘くなる。レビューや検証は、別のサブエージェントや決まった評価基準に任せる。

## 7. 最小構成から始め、モデルが賢くなったら削る
ハーネスの各部品は、「モデルにはこれができない」という前提を表している。どの失敗を防ぐかを言えない部品は足さない。モデルが進化したら前提を見直して取り除く。

## 8. 1つを正にして、ほかは参照する
同じ内容を2か所に書かない。片方だけ直されて食い違うため。エージェントへの指示は `AGENTS.md` に、hook の処理は1つのスクリプトに書き、ツールごとのファイルはそれを参照するだけにする。原則（`guidelines/`）・決定（`decisions.md`）・今の状態（`progress.md`）・失敗（`failures.md`）は役割で分ける。`AGENTS.md` の禁止事項だけは、ガイドラインを入れない構成でも守らせる最小限として、ガイドラインと重なってよい。

## 9. 決定には不採用案も残す
判断の理由と、採らなかった案とその理由を残す。記録がないと、エージェントは良かれと思って一度やめた案に戻してしまう。

## 10. 継ぎ足さず、変更後の全体として書き直す
部品やルールを足すときは、既存の構成のどこに入るかを考え、変更したファイルを最初からそう書かれていたかのように整える。注記・例外・新しい節を末尾に足していくと、全体の構成が読み取れなくなる。生成先のプロジェクトにも、同じ考え方をガイドラインと AGENTS.md で伝える。
