# 設計の見せ方と生成のしかた

SKILL.md の「3. 設計」と「4. 生成」の詳細。テンプレートは `assets/templates/` にある。

## 設計の見せ方

ファイルを作る前に、次の形で設計をユーザーに見せて合意を取る。作らないものには理由を書く。

```
レベル: L1
作るもの:
  - AGENTS.md / CLAUDE.md
  - README.md（既存のものを、テンプレートの構成に合わせて書き直す案）
  - docs/failures.md: エージェントが繰り返した失敗と対策
  - docs/guidelines/: documentation.md, design.md, coding.md
  - scripts/hooks/: 危険なコマンドを止める、編集したファイルを prettier で整形する
  - .claude/settings.json: .env の読み取りの禁止、読み取りとテストのコマンドの許可、上のスクリプトを呼ぶ hook
  - .claude/agents/evaluator.md: 実装の後に、懐疑的に確かめる評価役
作らないもの（理由）:
  - .codex/hooks.json: Codex を使わないため
  - docs/guidelines/ui.md: UI がないため
  - feature_list.json, init.sh: 長時間の自律作業を任せないため
  - docs/goal.md: L2 ではなく、大枠を残したいとも言われていないため（目的と扱わない範囲は AGENTS.md の概要に書く）
```

## テンプレートと生成先

| テンプレート | 生成先 | レベル | 用途 |
|---|---|---|---|
| `AGENTS.md` | `AGENTS.md` | 全部 | 概要、どこに何があるか、作業ルール |
| `claude-instructions.md` | `CLAUDE.md` | 全部（Claude Code） | `@AGENTS.md` と、Claude Code 固有の指示 |
| `README.md` | `README.md` | 全部 | 概要・起動方法・案内だけ |
| `goal.md` | `docs/goal.md` | L2、または大枠を残したいとき | オーナーの意思としての目標。エージェントは書き換えない |
| `failures.md` | `docs/failures.md` | L1〜 | 誰に起きてもおかしくない失敗と対策、対策の置き場所の選び方 |
| `guidelines/*.md` | `docs/guidelines/*.md` | L1〜 | 設計で選んだものだけをコピー |
| `scripts/hooks/*.sh` | `scripts/hooks/*.sh` | L1〜 | hook の処理の本体。Claude Code と Codex で共有 |
| `claude-settings.json` | `.claude/settings.json` | L1〜（Claude Code） | 権限設定と、スクリプトを呼ぶ hook |
| `codex-hooks.json` | `.codex/hooks.json` | L1〜（Codex） | スクリプトを呼ぶ hook |
| `claude-agents/evaluator.md` | `.claude/agents/evaluator.md` | L1〜（Claude Code） | 実装の後に懐疑的に確かめる評価役。コードは直さない |
| `feature_list.json` | `feature_list.json` | L2 | タスク一覧 |
| `init.sh` | `init.sh` | L2 | セッション開始時の起動スクリプト |

`CLAUDE.md` のテンプレートは、生成先と違う名前（`claude-instructions.md`）で置いてある。Claude Code は、読んだファイルのあるフォルダの `CLAUDE.md` を指示として読み込むので、同じ名前だと、skill のフォルダがプロジェクトの中にあるときに、テンプレートがそのプロジェクトの指示に混ざるため。

判断や作業の進み具合を書く記録のファイルは作らない。今の状態は git の状態とコミットメッセージから、判断の理由はコードのコメントとコミットメッセージから、構成は `AGENTS.md` の「どこに何があるか」から読み取らせる。コードと別に記録を持つと、同じことを二重に書くことになり、片方だけが古くなるため。失敗の記録だけは作る。同じ失敗が2回目かを、セッションをまたいで判断する手がかりがほかにないため。

設計で qa や performance を入れると決めたら、テンプレートはないので、[framework.md](framework.md) の「評価する役の分け方」と evaluator のテンプレートを元に `.claude/agents/` に作る。試す流れや測るコマンドはこのプロジェクトに合わせて書き、呼ぶ場面を `description` と `CLAUDE.md` に具体的に書く。qa の frontmatter には `model: haiku` を入れる。操作の結果（画面の snapshot など）の出力が多く、トークンを使うため。evaluator は、指摘の質を落とさないよう、モデルを指定せずに呼び出した会話のモデルで動かす。

## テンプレートの埋め方

テンプレートには、消す行を決める目印、埋める箇所、生成先にそのまま残す案内の3種類がある。

| 種類 | テンプレートでの形 | 生成するとき |
|---|---|---|
| 消す行を決める目印 | `<!-- L1 -->` | L1 以上でだけ行・節を残す。L0 では消す（参照先のファイルを作らないため） |
| | `<!-- L2 -->` | L2 でだけ行・節を残す |
| | `<!-- UI -->` | 画面があるプロジェクトでだけ行を残す |
| | `<!-- GOAL -->` | 目標のファイル（`docs/goal.md`）を作るときだけ行を残す |
| | `<!-- DATA -->` | データを保存する（ファイル・DB・ブラウザの保存領域など）プロジェクトでだけ節を残す（`coding.md`） |
| | `<!-- UI\|SERVER -->` | 画面があるか、サーバーとしてリクエストを受けるプロジェクトでだけ節を残す（`coding.md`） |
| | `<!-- YOMIYASU -->` | 生成するファイルが日本語で、yomiyasu がプロジェクトの中に git で共有されているときだけ行を残す（下の「人が読むファイルの推敲」） |
| 埋める箇所 | `<!-- PROJECT: … -->`、`# PROJECT: …`、`TODO` | プロジェクトの内容で埋める。スクリプトの中の目印だけの行（`block-dangerous.sh` の、止めるプロジェクト固有の操作など）は、足すものがなければその行を消す |
| | `feature_list.json` の空の文字列 | 実際の内容に置き換える |
| 残す案内 | `failures.md` の「（記入例）」の項目 | 記録の形を示す例として残す。生成先で最初の失敗を記録するときに置き換えられる |

残す行からも目印は消す。生成物に残ってよいのは、「残す案内」だけ。

- コマンドは、実際に実行して動くことを確かめてから書く。依存を入れる前などでまだ実行できないものは、ユーザーに聞くか、推測した形にコマンドの後ろで「（未確認）」を付けて書き、生成の最後の報告の「次にやること」に入れる。プロジェクトで使わない検証（型チェックのない言語の型チェックなど）は、未確認とせず行から外す。まだ入口のないコマンド（コードを書く前の起動など）は、推測で書かず「決めたらここに書く」とする。テスト・lint・型チェックは、通った項目を並べず失敗だけを出す形（例: テストの実行器の `--reporter=dot`）にし、失敗したときに場所と理由が出ることも確かめる。出力は毎回会話に残り、作業のあいだ膨らみ続けるため。警告を隠すオプション（ESLint の `--quiet` など）や、`| tail` で切る形は使わない。直すべき警告や失敗の詳細が見えなくなるため
- 画面があるプロジェクトでは、`AGENTS.md` の「画面の確認」に、開く URL と使うツールに加えて、出力を絞る使い方を書く（Playwright MCP なら、snapshot は `depth` や `target` で見たい所に絞り、画面写真は見た目を確かめるときだけ撮る）。snapshot や画面写真は会話に残り、長い作業で膨らむため
- `docs/goal.md` には、ヒアリングで聞いたオーナーの言葉を元に、あまり変わらないことだけを書く。完成の条件は確かめられる形（「〜できる」）にし、空欄は推測で埋めずにユーザーに聞く
- 生成するファイルの言語は、ユーザーの言語（既存ドキュメントがあればその言語）に合わせる
- 人が読むファイルの推敲: 生成するファイルが日本語で、使えるスキルの一覧に yomiyasu（AI が書いた日本語の不自然な比喩や主語のあいまいさを直すスキル）があるときは、生成した人向けのファイル（`README.md` と、作るなら `docs/goal.md`）を書き終えたあとに yomiyasu で推敲する。AI が書いた日本語に残りやすいクセを、人が読むファイルから除くため。`AGENTS.md`・`CLAUDE.md`・ガイドラインなどエージェント向けのファイルは推敲しない。yomiyasu は名前を出して頼まれるか、指示のファイルで求められたときしか読まれないので、生成先で使い続けるには指示の行が要る。行は、`AGENTS.md` の `<!-- YOMIYASU -->` の行と同じ文（名前だけは下のとおり一覧に合わせる）で、置く先は yomiyasu のある場所で決める。場所は一覧からは分からないので、プロジェクトの `.claude/skills/yomiyasu/` と `.agents/skills/yomiyasu/` があるか、`git ls-files` で追跡されているか（`.gitignore` で外していないか）を見る。プラグインで入れたものは、プロジェクトの `.claude/settings.json` で有効にしていればプロジェクトの中、`~/.claude/` 側だけなら利用者のフォルダとして扱う
  - プロジェクトの中にあり git で共有されている: `AGENTS.md` の行を残す。全員の環境にあるため。まだコミットしていなくても、`.gitignore` で外しておらず、このハーネスと一緒にコミットする予定なら共有とみなす
  - 利用者のフォルダ（`~/.claude/skills/` など）にだけある（プロジェクトの中にあっても git で共有しないものを含む）: `AGENTS.md` からは行を消す。どのプロジェクトでもその人だけが使えるスキルなので、指示もその人のユーザー設定（`~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md` など）に置く。使うエージェントごとにそのユーザー設定を見て、人が読むドキュメントを yomiyasu で推敲する指示が、文言は違っても意味として入っていれば何もしない。なければ、同じ文を足すことを生成の最後の報告の「次にやること」で勧める（ユーザー設定は skill からは書き換えない）
  - 行と呼び出しに書く名前は、一覧の名前どおりにする（プラグインで入れたときは `yomiyasu:yomiyasu`）
- `AGENTS.md` は約100行以内に収める。書くのは、コードを読んでも分からないことだけ（オプションまで含めた正確なコマンド、真似してはいけない書き方、リポジトリにない決定、2回訂正したこと）。コードや設定を読めば分かること（ディレクトリやファイルの一覧、依存パッケージなど）は書かない。「プロジェクト概要」の目的・利用者・扱わない範囲・用語は、ヒアリングで聞いたことを書く
- 「どこに何があるか」は、フォルダやモジュールの単位で、grep では分からないことだけを10〜15行で書く。何を受け持つか、正となる場所（同じ計算や定義を1か所にまとめている場所）、依存してよい向き、仕様の文書と読むきっかけ。ファイル1つずつは並べない。移動や改名のたびに古くなり、行数も増えるため。リンクは実際にあるファイルだけにする。予定はあるがまだない文書は、リンクにせず、場所と「まだない。できるまでは推測で決めずにユーザーに聞く」を書く。空のフォルダで始めるときは、決めた構成を書き、まだ決めていない部分は「決めたらここに書く」とだけ書く
- 仕様の決まり（計算のしかた、端数の扱い、表示の形など）が文書にあるときは、`AGENTS.md` に中身を写さず、「どこに何があるか」に、その文書の場所と、読むきっかけ（「金額の計算に触れる前に `docs/pricing.md` を読む」）だけを書く。書き方の規約に見えても、決まりから来る中身（「切り捨ては `//`」のような端数の扱いなど）は写さない。写すと、仕様を変えたときに文書だけが直され、`AGENTS.md` に古い決まりが残るため。決まりを守らせる行（「決まりと違う計算をしない」など）は、ユーザーが決まりの変更を頼んだときと分けて書く（頼まれたら先に文書を直してから実装し、依頼にない変更が要るときだけ提案する）。分けないと、頼まれた仕様変更でも確認を求めて止まるため
- ガイドラインの原則は、コピーした後に書き換えない。目印の付いた行・節だけは、条件に合わなければ消し、消した節は入れなかったガイドラインと同じく設計の合意のときに伝える。入れなかったガイドラインへの参照も、すべて消す（`design.md` を入れないときの、`coding.md` の中の `（[design.md](design.md)）`。2か所あり、どちらも括弧ごと消せば文が通る）。リンク先のないリンクが残るため。ガイドラインを1つも入れないときは、`AGENTS.md` と evaluator から、ガイドラインを指す行を消す
- 調査・ヒアリングで決まった判断（レベル、入れなかった部品とその理由、作成時のツールとモデル）は、生成の最後の報告に書き、ハーネスを入れるコミットのメッセージにも書くよう勧める（skill がコミットするときは自分で書く）。ツールとモデルは、更新されたときにハーネスを見直すきっかけにするため
- 生成先で skill を作るときは、ツールの大きさの上限に収める（[agent-tools.md](agent-tools.md)）

## 既存のプロジェクトに入れるとき

- 既存ファイルは勝手に上書きせず、差分で提案する
- 既存の内容に継ぎ足さず、テンプレートの構成に合わせて全体を書き直した案を出す（[principles.md](principles.md) の原則10）。既存の内容で残すべきものは、テンプレートのどの節に入るかを決めて移す

## 守らせる仕組み

- hook の処理はスクリプトに書き、ツールごとの設定はそれを呼ぶだけにする。formatter と lint は、pre-commit と CI にも置くことを提案する（[agent-tools.md](agent-tools.md)）
- formatter が決まっていない、または決まっていてもまだ実行できない（依存を入れる前の新しいプロジェクトなど）ときは、`format-changed.sh` とそれを呼ぶ hook は入れず、formatter を実行できるようになったら入れることを、生成の最後の報告の「次にやること」に書く。`AGENTS.md` の formatter の行は、ほかの確かめられないコマンドと同じく「（未確認）」を付ける。実行できない formatter を呼ぶ hook は、ファイルを編集するたびに失敗を返し、作業を止めるため
- `.claude/settings.json` の `allow` には、`AGENTS.md` に書いたテスト・lint・型チェックのコマンドも、引数まで含めた完全な形で足す（書き方の注意は [agent-tools.md](agent-tools.md)）。「（未確認）」のコマンドは足さない。確かめると形が変わることが多く、使われない許可や、思わない形を確認なしで通す許可が残るため。確かめて印を消すときに足すことは、`CLAUDE.md` のテンプレートに書いてある
- 手元に本物の秘密情報（`.env` など）を置くプロジェクトでは、`Read` の `deny` だけでは Bash から読める抜け道が残ることを伝え、サンドボックスを有効にするか、秘密情報をプロジェクトの外に置くかを提案する（[agent-tools.md](agent-tools.md)）
- 画面を確かめる MCP（Playwright MCP など）を入れたら、`.claude/agents/evaluator.md` の `tools` にもそのツールを足す（qa を作るなら qa にも）。`tools` に挙げたツールしか使えないため
- 無人実行などで `dontAsk` モードを使うプロジェクトでは、`.claude/agents/evaluator.md` から `permissionMode` の行を消す。評価役だけが許可リスト以外の操作も通すようになるため（[agent-tools.md](agent-tools.md)）
- Codex 用の hook を作ったら、ユーザーに Codex 上で hook の定義を確認・信頼してもらう（信頼されるまで実行されない）
