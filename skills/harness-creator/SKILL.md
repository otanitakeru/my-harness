# Harness Creator

プロジェクトに合ったハーネスを作り、使いながら改善する。流れは 調査 → ヒアリング → 設計 → 生成 → 検証 → 育成。ユーザーがどの段階にいるかを判断して、そこから始める（新規プロジェクトなら調査から、「エージェントが同じミスをする」なら育成から）。

| ファイル | 内容 | 読むタイミング |
|---|---|---|
| [references/principles.md](references/principles.md) | ハーネスの設計原則（判断の根拠） | 最初に必ず |
| [references/framework.md](references/framework.md) | 部品の一覧、レベル、ガイドラインの選び方、失敗と対策の置き場所 | 最初に必ず |
| [references/concepts.md](references/concepts.md) | どのプログラムにも共通する概念（調査・ヒアリングの項目と、書く場所） | 調査の前 |
| [references/generation.md](references/generation.md) | 設計の見せ方、テンプレートの一覧と目印、埋め方 | 設計の前 |
| [references/agent-tools.md](references/agent-tools.md) | Claude Code と Codex での書き方、hook・pre-commit・CI の使い分け | 生成の前 |

## 1. 調査

ユーザーに聞く前に、自分で分かることは調べる。新規で中身が空なら飛ばす。

- 既存のエージェント設定（`AGENTS.md`, `CLAUDE.md`, `.claude/`, `.codex/`, `.cursor/` など）。あれば上書きせず、そこから始める
- pre-commit と CI の設定、既存のドキュメント（`README.md`, `docs/`）
- git を使っているか。使っていなければ `git init` を提案する（経緯は git の履歴に任せる設計のため）
- 言語・フレームワーク・パッケージマネージャ、実行・検証コマンド、UI があるか
- [concepts.md](references/concepts.md) の各項目で、分かったこと・分からないこと

## 2. ヒアリング

調査で埋まらなかった項目だけを、重要なものから数個ずつ聞く。必ず確認すること:

- 何を作るか、誰が使うか、今は扱わない範囲
- エージェントにどこまで任せたいか（提案だけ / 実装まで / 長時間の自律作業まで）→ レベルの判断に使う
- 絶対にやってほしくないこと、「完了」と言ってよい条件
- コミットの方針。迷っていれば、L2 は作業単位ごと、それ以外は指示があるときだけを推奨する
- 使うエージェント（Claude Code / Codex / 両方）。使うものの設定だけを生成する

## 3. 設計

[framework.md](references/framework.md) に従って、レベル（L0〜L2）、入れる部品、入れるガイドラインを決める。どの失敗を防ぐかを言えない部品は入れない（原則7）。ファイルを作る前に、[generation.md](references/generation.md) の形で設計を見せて合意を取る。

## 4. 生成

[generation.md](references/generation.md) に従い、テンプレートを元にプロジェクト固有の内容で埋めたファイルを作る。既存のプロジェクトでは、上書きせず、テンプレートの構成に合わせて全体を書き直した案を出す（原則10）。

## 5. 検証

- 生成物に目印（`PROJECT`、`TODO`、`<!-- L1 -->` など）が残っていない。AGENTS.md と README.md のリンク先がすべてある
- AGENTS.md に書いたコマンド（起動・テスト・lint・formatter）を実行し、すべて動く
- `.claude/settings.json` と `.codex/hooks.json` が正しい JSON。hook のスクリプトに止めるべき入力と通すべき入力を渡し、終了コードが期待どおり（止めるなら 2、通すなら 0）
- AGENTS.md の各行について、その行がなければエージェントがこのプロジェクトで間違えるかを考え、間違えない行（どのプロジェクトにも言える一般論、コードを読めば分かること）は消す
- 生成した各ファイルを頭から読み、テンプレートの継ぎはぎではなく、このプロジェクトのために書かれたように読める
- 可能なら、サブエージェントに AGENTS.md だけを読ませて小さなタスクを1つこなさせ、迷った点や間違えた点を直す

検証できなかった項目は、ユーザーに伝える。

## 6. 育成

- 失敗を伝えられたら、まず `docs/failures.md` に記録する。1回目なら記録だけでよい
- 部品を足す・移す・削る判断は、[framework.md](references/framework.md) の「部品を見直すタイミング」に従う。入れる先のファイルには継ぎ足さず、その構成のどこに入るかを決めて書き直す
- 対策を入れたら、`docs/failures.md` の該当項目を「対策済み」にし、何をどこに入れたかを書く
- プロジェクトをまたいで役立つ改善に気づいたら、この skill のテンプレート側への反映を提案する

## ユーザーとのやり取り

- 専門用語（hook、サブエージェントなど）は、知っている様子がなければ一言で説明する
- 選択肢を並べるだけでなく、推奨を1つ示す
- 最後に、生成したファイルとそれぞれの目的、未確認の項目を伝える。テンプレートが合わなかった箇所と、判断に迷った点も伝える（skill の改善に使うため）
- Claude Code の設定を生成したときは、あわせて、実装は新しいセッションで始めるよう伝える。新しく作ったサブエージェントと MCP サーバーは、同じセッションでは使えないことがあり、そのまま実装すると評価役と画面の確認が働かないため。同じセッションで続けると言われたときの代え方は [agent-tools.md](references/agent-tools.md) の「skills とサブエージェント」にある
