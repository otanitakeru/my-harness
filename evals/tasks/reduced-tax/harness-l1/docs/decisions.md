# 設計判断の記録

要件と、**なぜそうしたか** を残す。原則（どう決めるか）は `docs/guidelines/` にあり、ここにはこのプロジェクトでの具体的な決定を書く。
古い判断は消さず、状態を「廃止」にして、やめた理由を書く。
判断は全部を読まず、見出しから関係するものを選んで読む。そのため見出しは、それだけで何を決めたかが分かる一文にする。

## 要件

- **目的**: 小さな店のレジで使う、買い物かごの金額計算、レシートの表示、返品の返金額の計算。料金の決まりは [pricing.md](pricing.md) が正
- **利用者**: 店のレジのプログラム（呼び出す側のコード）
- **扱わない範囲**: 画面、データベース、決済
- **用語**: 小計＝税抜きの合計、標準税率＝10%、軽減税率＝食品の8%

## 判断

### D-001 ハーネスは L1（実装まで任せる）で作り、Claude Code だけを対象にする

- **日付**: 2026-11-20
- **状態**: 採用
- **決定**: レベルは L1。`AGENTS.md`・`CLAUDE.md`、`docs/`（decisions・progress・failures・guidelines の documentation と coding）、`block-dangerous.sh` の hook、権限設定、evaluator を入れる。コミットは指示があるときだけ。作成時のツールとモデルは Claude Code / Sonnet 5.5
- **理由**: 実装まで任せるが、長時間の自律作業はしない。コードはモジュール3つの小さなもの
- **不採用案**: L2（`feature_list.json`・`init.sh`）は長時間の自律作業がないため入れない。`guidelines/design.md` は層に分けるほどのコードがなく、`ui.md` は画面がないため入れない。`.codex/hooks.json` は Codex を使わないため入れない。`format-changed.sh` と整形の hook は formatter が決まっていないため入れない。qa・performance は画面・API・性能の目標がないため入れない
- **見直す条件**: formatter・lint を決めたとき、画面や決済を扱うとき、モデルを更新したとき

### D-002 料金の決まりは docs/pricing.md を正とし、AGENTS.md には写さない

- **日付**: 2026-11-20
- **状態**: 採用
- **決定**: 税・レシート・返品の決まりは `docs/pricing.md` だけに書き、`AGENTS.md` からは場所と読むきっかけだけを示す
- **理由**: 2か所に書くと、決まりを変えたときに片方が古くなるため
- **不採用案**: `AGENTS.md` に税率や端数の規則を写す案。食い違いの原因になる
- **見直す条件**: 決まりの文書を複数に分けるとき
