# AGENTS.md

このプロジェクトで作業する AI エージェント向けの地図です。

## プロジェクト概要

小さな店のレジで使う、買い物かごの金額計算、レシートの表示、返品の返金額の計算。Python 3.10 以上、標準ライブラリだけ。画面・データベース・決済は今は扱わない。

## 最初に読むもの

| 目的 | 場所 |
|---|---|
| 今の状態と次にやること | [docs/progress.md](docs/progress.md)（自分の分は `docs/local/progress.md`） |
| 料金の決まり（税・レシート・返品） | [docs/pricing.md](docs/pricing.md) |
| 要件と設計判断（なぜそうしたか） | [docs/decisions.md](docs/decisions.md) |
| 原則（どう決めるか） | [docs/guidelines/](docs/guidelines/)（documentation.md, coding.md） |

実装・レビューの前に、`docs/decisions.md` の「要件」の節を全部読み、判断とガイドラインは見出しから関係するものだけを選んで読むこと。見出しは `grep -n "^##" docs/decisions.md docs/guidelines/*.md` で一覧にする。

金額・税・レシート・返金に触れる前に、`docs/pricing.md` を読む。

## コマンド

- 起動: なし（ライブラリ。使い方は [README.md](README.md)）
- テスト: `python3 -m unittest -q`（1つのテストだけを実行: `python3 -m unittest -q tests.test_cart.CartTest.test_empty_cart_is_zero`）
- lint / 型チェック: 未確認（決まっていない）
- formatter: 未確認（決まっていない）

起動方法が分からないまま作業を始めない。調べて分かったことは、この節に書き足す。

## 作業の進め方

### 開始時
- `docs/progress.md`、`docs/local/progress.md`、`git log --oneline -20`、`git status` を読み、今の状態を把握する。`docs/local/progress.md`・`failures.md` がなければ（clone した直後など）、`docs/` の同じ名前のファイルの冒頭の案内に従って作る
- テストを一度動かし、作業前の時点で壊れていないか確認する。壊れていたら、新しい作業より先に報告する

### 着手前
- 期待する挙動・今回扱わない範囲・確認方法を明確にする
- 次のときは、書き始める前に自分の受け取り方を返し、返事を待つ: 依頼が複数の意味に取れる、判断を左右する不明点がある、変更が広いか取り消しにくい（多くのファイル、設計や公開の形、削除・移動）、短い依頼に自分で補った前提が多い。迷っていなくても書く。書いて見せると、自分では気づかない読み違いが見えるため。次の4行だけにし、例や理由は足さない
  - 受け取った内容: …
  - やること: …（やらないことも、ひと言で）
  - 別の読み方: …（いちばんありそうな1つ。思い当たらなければこの行は書かない）
  - これで進めてよいですか？
- 誤字の修正や、言われたとおりの1か所の変更など、小さく取り消しやすい作業は返さずに進めてよい。置いた前提は報告で伝える
- 変更が入るまとまり（関数・モジュール・ドキュメントの節）を特定し、変更後にそのまとまりがどういう形になるかを考えてから書き始める
- 依頼が `docs/decisions.md` の方針とぶつかるときや、もっと良い案があるときは、実装の前に懸念と代案を出す
- 仕様・データモデル・設計方針を変えるときは、実装より先に、それを書いた文書（`docs/decisions.md` や仕様の文書）を直す

### 作業中
- 変更するのは、目的に関係するまとまりだけ。関係しないもの（無関係な整形・改名・依存更新・リファクタリング）には触らず、既存の作業中の変更も消さない
- 関係するまとまりは、継ぎ足さずに変更後の全体として書き直す。最初からその仕様だったかのような形にし、変更の経緯はコードやコメントに残さない
- 局所的な修正でも、全体の規約（型・命名・層の分け方・共通化の基準）に合わせる
- 依頼にない機能・設定項目・抽象化は足さない。依頼の範囲外に改善点を見つけても、その場では変更せず提案に留める
- 読むのは必要な部分だけにする。大きなファイルや、長すぎて別のファイルに保存されたコマンドの出力は、grep や行の範囲を指定して読み、丸ごと読み直さない。複数のファイルをまとめて `cat` しない。読んだものはすべて会話に残り、作業のあいだ膨らみ続けるため
- 長い作業では、きりのよいところで progress.md を今の状態に書き換え、会話がいつ圧縮されても再開できるようにする。依頼の途中で会話が長くなったら、書き換えてから、会話を要約して続けるコマンド（Claude Code の `/compact` など）を使うよう勧める

### 完了の条件
- `python3 -m unittest -q` が通り、`docs/pricing.md` の決まりを満たしていることを、テストの実行結果と決まりとの突き合わせで確認する。決まりの項目に対応するテストがなければ、先にテストを足す
- 変更したまとまりを、差分ではなく頭から読み直し、前の版を知らない人が読んでも最初からこう書かれていたように見えるか確かめる。意図しない変更が入っていないかは差分で確かめる
- 報告は短く、結論（何ができて今どういう状態か、1〜2行）→ **未確認の事項**と失敗した確認 → 次にやること（ユーザーの判断や作業が要るものを先に）の順で書く。確認していないことを「動きます」と書かない。通った確認と作業の細目は一言にまとめ、差分・コミット・`docs/` を指す。長い報告は読まれず、会話も膨らむため

### 終了時
- 記録は、このリポジトリで作業する誰にでも当てはまることだけを `docs/` に書き、一人の作業の途中経過や、その人の環境・使い方でだけ起きることは、git に入れない `docs/local/` に書く。迷ったら `docs/local/` に書く。`docs/` の記録は全員のエージェントが指示として読むため
- `docs/progress.md` と `docs/local/progress.md` を今の状態に **書き換える**（追記しない）
- 依頼が終わったら、次の依頼は新しいセッションで始めるよう伝え、最初に送る一文（例: 「progress.md の次にやることの1から始めて」）を添える。続きは `docs/` から読み直せるので、長い会話を持ち越すより古い細部を取り違えにくい
- 後から理由が必要になる判断は、`docs/decisions.md` に残す（不採用案とその理由も）
- 自分の失敗に気づいた・指摘されたときは、`docs/failures.md` の使い方に従って、そこか `docs/local/failures.md` に書く
- コミット: 指示があるときだけ行う

## 承認が必要な操作

次の操作は、対象・影響範囲・復旧方法を示し、明示的な承認を得てから行う。

- 取り消しの難しい git 操作（`git push --force`, `git reset --hard` など）やファイルの再帰的な削除
- 外部への送信

## 禁止事項

- `docs/pricing.md` の決まりと違う計算をすること。決まりの変更を頼まれたときは、先に `docs/pricing.md` を直してから実装する。頼まれていない変更が要ると気づいたときは、変えずに提案する
- テストを削除・無効化・緩めて通すこと。決まりの変更でテストを直すときは、仕様に合わせて直した理由を報告に書く
- 失敗を握りつぶすこと（空の catch、エラーの無視）
- 秘密情報や実在の個人情報を、コード・ログ・コミット・テストデータに含めること

## このファイルの育て方

- エージェントが同じミスを2回したら、防止策を入れる。置き場所の選び方は `docs/failures.md` にある
- ルールを足すときは、末尾に足さず、既存の節のどこに入るかを考えて書き直す。一人だけの好みや環境の事情はここに書かず、その人のユーザー設定（`~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md` など）に置く
- 約100行を超えたら、詳しい内容を `docs/` に分け、ここにはリンクだけ残す

## プロジェクト固有のルール

- 金額は円の整数だけで扱い、`float` や `/` を使わない（切り捨ては `//`）。決まりは `docs/pricing.md`
