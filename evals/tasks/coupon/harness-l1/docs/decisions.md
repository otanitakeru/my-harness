# 設計判断の記録

要件と、**なぜそうしたか** を残す。原則（どう決めるか）は `docs/guidelines/` にあり、ここにはこのプロジェクトでの具体的な決定を書く。
古い判断は消さず、状態を「廃止」にして、やめた理由を書く。
判断は全部を読まず、見出しから関係するものを選んで読む。そのため見出しは、それだけで何を決めたかが分かる一文にする。

## 要件

- **目的**: 小さな店のレジで使う、買い物かごの金額計算とレシートの表示
- **利用者**: 店のレジのプログラム（呼び出す側のコード）
- **扱わない範囲**: 画面、データベース、決済
- **用語**: 料金の計算の決まりは `docs/pricing.md` が正。金額の計算・レシートの形式・クーポンの扱いで迷ったら、先にそれを読む

### D-001 ハーネスはレベル L1・Claude Code だけで作り、formatter の hook は入れない

- **日付**: 2026-11-19
- **状態**: 採用
- **決定**: エージェントには実装まで任せる（L1）。使うのは Claude Code だけで、`.codex/` は作らない。コミットは指示があるときだけ。ガイドラインは `documentation.md` と `coding.md` だけを入れた。作成時のツールとモデルは Claude Code / Sonnet 5.5
- **理由**: 長時間の自律作業は任せないので、`feature_list.json` と `init.sh`（L2）は要らない。画面がないので `ui.md` は要らない。`cart.py` と `receipt.py` の2モジュールだけで層を分ける規模ではないので `design.md` は要らない。formatter・lint が決まっておらず、実行できない formatter を呼ぶ hook は編集のたびに失敗するので、`format-changed.sh` も入れなかった
- **不採用案**: formatter の hook を先に入れておく案。実行できないものを呼ぶと作業が止まるため採らなかった
- **見直す条件**: formatter・lint を決めたとき。コードが増えてモジュールや層を分けるとき（`design.md` を入れる）。モデルを更新したとき

### D-002 料金の計算の正は `docs/pricing.md` に置き、実装とテストをそれに合わせる

- **日付**: 2026-11-19
- **状態**: 採用
- **決定**: 金額・消費税・クーポン・レシートの決まりは `docs/pricing.md` に書く。実装がそれと食い違うときは実装を直す。決まり自体を変えるときは、実装の前にユーザーに確認して `docs/pricing.md` を直す
- **理由**: 料金の計算は、動いていても決まりと違えば間違いになる。決まりの文書が1つなら、テストと実装が同じ誤解をしても見つけられる
- **不採用案**: テストを正とする案。テストが決まりと違う内容で書かれていても気づけないため採らなかった
- **見直す条件**: 決まりの文書を別の形（表やデータ）に移すとき
